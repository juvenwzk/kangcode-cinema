## 1. 环境变量

`application-prod.yml` 已全部用 `${VAR:默认值}` 注入，**不需要改配置文件**，只要在启动时提供变量。
命令行参数优先级高于配置文件，所以直接跟在 `java -jar` 后面最稳。

| 变量 | 说明 | 示例 |
| --- | --- | --- |
| `DB_HOST` | MySQL 主机 | `127.0.0.1` |
| `DB_PORT` | MySQL 端口 | `3306` |
| `DB_NAME` | 库名 | `railway` |
| `DB_USER` | 数据库账号 | `root` |
| `DB_PASSWORD` | 数据库密码 | `******` |
| `REDIS_HOST` | Redis 主机 | `43.166.0.94` |
| `REDIS_PORT` | Redis 端口 | `6379` |
| `REDIS_PASSWORD` | Redis 密码（无密码留空） | `123456` |
| `RABBITMQ_HOST` | RabbitMQ 主机 | `43.166.0.94` |
| `RABBITMQ_PORT` | RabbitMQ 端口 | `5672` |
| `RABBITMQ_USER` | RabbitMQ 账号 | `admin` |
| `RABBITMQ_PASSWORD` | RabbitMQ 密码 | `******` |

> ⚠️ 生产环境请用**密钥管理**（K8s Secret / 环境变量注入）传入密码，不要写死进 git。

## 2. 启动命令

```bash
# 1. 构建（跳过测试；发布前单测已在 CI/本地跑过）
mvn clean package -DskipTests

# 2. 启动（用 prod 环境 + 环境变量注入）
java -jar server/target/server-1.0.0-SNAPSHOT.jar --spring.profiles.active=prod \
  --DB_HOST=127.0.0.1 \
  --REDIS_HOST=43.166.0.94 \
  --REDIS_PASSWORD=123456 \
  --RABBITMQ_HOST=43.166.0.94 \
  --RABBITMQ_USER=admin \
  --RABBITMQ_PASSWORD=123456
```

看到 `KangRail 康轨铁路购票系统启动成功` 即为起来。

> 本机部署（JDK 17+、Maven 见 README 第 5 章）示例：

## 3. 端口放行

| 端口 | 用途 | 是否对外 |
| --- | --- | --- |
| `8080` | 业务 HTTP | ✅ 只放这个 |
| `3306` | MySQL | ❌ **绝不放公网** |
| `6379` | Redis | ❌ **绝不放公网**（Redis 未鉴权时被扫到会被挖矿/写 shell） |
| `5672` / `15672` | RabbitMQ AMQP / 管理台 | ❌ 管理台仅内网/VPN |

> 参考开发计划「坑 7」：中间件端口暴露到公网是真实事故源头。

## 4. 健康检查（部署后第一件事）

```bash
curl http://localhost:8080/actuator/health
```

预期（`status=UP` 才算成功）：

```json
{"status":"UP","components":{
  "db":{"status":"UP"},
  "redis":{"status":"UP"},
  "rabbit":{"status":"UP"},
  "diskSpace":{"status":"UP"},
  "ping":{"status":"UP"}
}}
```

- 一次就能确认 **MySQL / Redis / RabbitMQ 三个中间件通不通**，比逐个手测快。
- 哪个 component 不是 `UP`，就对着它去查（开发计划第十章排错手册）。
- 指标（可选）：`curl http://localhost:8080/actuator/metrics/http.server.requests`

## 5. 回滚步骤

**发布即备份**：上线前把当前在跑的 jar 备份一份。

```bash
# 备份旧版本
cp server-1.0.0-SNAPSHOT.jar server-1.0.0-SNAPSHOT.bak.jar
```

**回滚 = 换回旧 jar + 重启**：

```bash
# 1. 停新进程
#    （本机演示：找到 pid 后 kill；容器环境用 docker stop / kubectl rollout undo）
kill <new_pid>

# 2. 换回旧 jar
cp server-1.0.0-SNAPSHOT.bak.jar server-1.0.0-SNAPSHOT.jar

# 3. 重启
java -jar server-1.0.0-SNAPSHOT.jar --spring.profiles.active=prod ...

# 4. 再验一次健康
curl http://localhost:8080/actuator/health
```

> **发布/回滚双通道**演练记录（任务 6-4）：
> 1. 备份当前 jar → `server-1.0.0-SNAPSHOT.bak.jar`
> 2. 改一行日志文案 → `mvn package` 出新 jar
> 3. 停旧进程、起新 jar、`/actuator/health` 确认 `UP`
> 4. 模拟回滚：停新进程、换回 `.bak.jar`、重启、再验 `health`
> 5. 全程命令即本节 1~4 步

## 6. 日志位置

| 环境 | 输出 | 位置 |
| --- | --- | --- |
| 本机/容器前台 | 控制台（ConsoleAppender，见 `logback-spring.xml`） | 标准输出 / `docker logs <容器>` |
| 服务器后台 | 重定向到文件 | 例：`nohup java -jar ... > /var/log/kangrail/app.log 2>&1 &` |

- 日志格式含 **TraceId**：`2026-10-16 22:00:00.123 [http-nio-8080-exec-1] [a1b2c3d4] INFO ... c.k.s.c.XXX - ...`
- 排查一次请求：拿它的 `[traceId]` 直接 `grep`，能把拦截器→service→mapper 的完整轨迹一次捞全：
  ```bash
  grep "a1b2c3d4" /var/log/kangrail/app.log
  ```
