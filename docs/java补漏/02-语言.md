## 第 1 章　集合：为什么容量必须是 2 的幂

### 1.1 现象

你项目里几乎没创建过集合（只有一个 `new ArrayList`），但面试一定问 `HashMap`。
先从一个最容易答错的问题开始：

> **`new HashMap(17)` 的容量是多少？**

答案是 **32**。因为 `HashMap` 会把容量向上取整到最近的 2 的幂（`tableSizeFor`）。

### 1.2 为什么非得是 2 的幂

因为算数组下标用的是**取位与**，不是取模：

```java
index = (n - 1) & hash;      // n 是容量
```

当 `n` 是 2 的幂时，`n-1` 的二进制是**全 1**（比如 16 → `1111`），
`&` 运算的结果分布最均匀。

如果 `n = 15`（不是 2 的幂），`n-1 = 14 = 1110`，
那么 `&` 的结果**最后一位永远是 0** → 所有元素只能落在偶数下标 → **一半的桶永远用不到**。

**这就是"2 的幂"的真正原因：不是为了取模方便，是为了让位与之后的分布均匀。**

### 1.3 扰动函数：为什么还要 `h ^ (h >>> 16)`

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

因为下标只用到 hash 的**低几位**，高位全被 `&` 丢掉了。
把高 16 位异或到低 16 位，**让高位也参与运算**，减少冲突。

### 1.4 扩容时元素怎么搬

不是全部重新算 hash，而是看**多出来的那一位**：

```java
if ((e.hash & oldCap) == 0) {
    // 留在原位置 j
} else {
    // 移到 j + oldCap
}
```

举例：容量 16 → 32，`oldCap = 16 = 10000`
- hash 的这一位是 0 → 留在原桶
- 是 1 → 移到 `原位置 + 16`

**这个设计让扩容时不用重算 hash，而且元素要么不动、要么整段平移。**

### 1.5 链表什么时候变红黑树

| 条件 | 值 |
| --- | --- |
| 链表长度 | ≥ **8** 转树 |
| 树节点数 | ≤ **6** 退化回链表 |
| 数组容量 | ≥ **64**（不够就先扩容，不转树） |

为什么是 8：泊松分布下，链表长度到 8 的概率约 0.00000006，属于极端情况。
**阈值设成 8 是为了"正常情况下几乎不转树"，避免树化开销。**

### 1.6 ArrayList 扩容是 1.5 倍

```java
int newCapacity = oldCapacity + (oldCapacity >> 1);   // 1.5 倍
```

为什么不是 2 倍：1.5 倍在"空间浪费"和"扩容次数"之间更平衡（2 倍浪费更多内存，频繁扩容又太慢）。

## 第 2 章　泛型：为什么运行时看不到 `<String>`

### 2.1 现象

```java
List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
System.out.println(a.getClass() == b.getClass());   // true
```

**两个不同类型的集合，运行时是同一个类。** 这就是**类型擦除**。

### 2.2 擦除带来了三个限制

| 你不能写 | 为什么 |
| --- | --- |
| `new T[10]` | 运行时不知道 T 是什么，没法分配数组 |
| `if (x instanceof List<String>)` | 运行时没有 `<String>` 这个信息 |
| `catch (MyException<String> e)` | 同上 |

**能写的替代方案**：`(T[]) new Object[10]` + `@SuppressWarnings`，或者传一个 `Class<T>` 参数。

### 2.3 通配符：PECS 原则

> **Producer Extends, Consumer Super**
> 你只从里面**读**（生产者）→ 用 `? extends T`
> 你只往里面**写**（消费者）→ 用 `? super T`

```java
// 只读：可以读成 Number，但不能 add
void printAll(List<? extends Number> list) {
    for (Number n : list) { }        // ✅ 能读
    // list.add(1);                  // ❌ 不能写
}

// 只写：可以 add Integer，但读出来只能是 Object
void fill(List<? super Integer> list) {
    list.add(1);                     // ✅ 能写
    Object o = list.get(0);          // 读只能当 Object
}
```

**为什么这么设计**：`List<? extends Number>` 可能是 `List<Integer>` 也可能是 `List<Double>`，
往里写 Integer 会破坏 Double 那个列表的类型安全。

### 2.4 你项目里其实已经在用泛型了

```java
public interface TrainOrderMapper extends BaseMapper<TrainOrder> { }
```

`BaseMapper<T>` 就是泛型：MyBatis-Plus 靠 T 知道该操作哪张表。
`Result<T>` 也是（`Result<OrderVO>`、`Result<Void>`）。

**试着回答**：为什么要设计成 `Result<T>` 而不是 `Result` 里放 `Object data`？
→ 因为泛型能在**编译期**发现类型错误；`Object` 要等到运行时强转才报错。

## 第 3 章　Stream：你现在只用过 `map + collect`

### 3.1 先看你项目里的那一处

```java
return orders.stream().map(this::toVO).collect(Collectors.toList());
```

这是 Stream 最基础的用法。**但它有一个特性你需要知道：惰性求值。**

```java
orders.stream()
      .map(o -> { System.out.println("处理 " + o.getOrderNo()); return toVO(o); })
      .map(this::something);
// 上面两行打完，什么都不会打印 —— 因为还没有"终止操作"
```

**中间操作（`map`/`filter`/`sorted`）只是"记下来"，遇到终止操作（`collect`/`forEach`/`count`）才真正执行。**

### 3.2 补三个最常用的

**① `filter` —— 过滤**

```java
// 只取待支付的订单
List<OrderVO> waiting = orders.stream()
        .filter(o -> o.getStatus() == 0)
        .map(this::toVO)
        .collect(Collectors.toList());
```

**② `groupingBy` —— 分组统计（最实用）**

场景：统计**每趟车次的订单数和总金额**。

```java
Map<Long, Long> countByTrain = orders.stream()
        .collect(Collectors.groupingBy(TrainOrder::getTrainId, Collectors.counting()));

Map<Long, Long> amountByTrain = orders.stream()
        .collect(Collectors.groupingBy(
                TrainOrder::getTrainId,
                Collectors.summingLong(TrainOrder::getTotalAmount)));
```

**③ `flatMap` —— 把嵌套结构摊平**

```java
// 一个订单有多个明细，想拿到所有乘客姓名
List<String> names = orders.stream()
        .flatMap(o -> o.getItems().stream())      // Stream<List<Item>> → Stream<Item>
        .map(TrainOrderItem::getPassengerName)
        .collect(Collectors.toList());
```

> `map` 是"一对一"，`flatMap` 是"一对多再摊平"。区别就这一句。

### 3.3 `parallelStream` 的三个坑（别乱用）

| 坑 | 说明 |
| --- | --- |
| 共用线程池 | 用的是 `ForkJoinPool.commonPool()`，**并行度 = CPU 核数 - 1**，会和其他 parallelStream 抢 |
| IO 密集没收益 | 它适合 CPU 密集。查数据库用 parallelStream，只是换了个地方排队 |
| 有状态操作会错 | 往 `ArrayList` 里 `add`、用非线程安全的累加器，结果会乱 |

**结论：你项目里的场景（查库、写库）都不要用 `parallelStream`。**

### 3.4 `Optional`：不是用来消灭 null 的

**正确心智**：`Optional<T>` 表示"**这个方法的返回值可能没有**"，是给**返回值**用的。

```java
// ✅ 好：调用方必须处理"没有"的情况
Optional<TrainOrder> find(String orderNo);

// ❌ 坏：字段用 Optional（不能序列化，MyBatis 也不支持）
private Optional<String> remark;

// ❌ 坏：参数用 Optional（直接重载方法或允许 null 更清楚）
void save(Optional<String> remark);
```

**一个必须知道的坑：`orElse` 和 `orElseGet` 的区别**

```java
// orElse：无论有没有值，参数里的方法都会执行
order.orElse(loadFromDb());        // ❌ 即使 order 有值，也会去查库！

// orElseGet：只有为空才执行
order.orElseGet(() -> loadFromDb()); // ✅
```

## 第 4 章　Java 17：你还没用上的语法

### 4.1 `record`：替代"只装数据"的类

你现在用 Lombok：

```java
@Data
@AllArgsConstructor
public class OrderVO { private String orderNo; private Long totalAmount; }
```

Java 17 可以写成：

```java
public record OrderVO(String orderNo, Long totalAmount) { }
```

自动生成：全参构造、访问器（`orderNo()` 不是 `getOrderNo()`）、`equals`/`hashCode`/`toString`。

| 对比 | Lombok `@Data` | `record` |
| --- | --- | --- |
| 可变性 | 可变（有 setter） | **不可变**（final 字段） |
| 依赖 | 需要 Lombok 插件 | 语言原生 |
| 适用 | 需要 setter 的实体/DTO | **只读的返回值、消息体** |

> 你项目里的 `OrderCreateMessage`、`StockReleaseMessage` 这类**消息体**，很适合改成 `record`。
> 但注意：MyBatis-Plus 的实体不能改（需要无参构造 + setter），`OrderVO` 有 builder 用法，也要慎重。

### 4.2 `var`：局部变量类型推断

```java
var orders = trainOrderMapper.selectList(wrapper);   // 自动推断成 List<TrainOrder>
```

**只能用于局部变量**，不能用于字段、方法参数、返回值。
好处是省掉重复的类型名；坏处是可读性下降（团队里要约定使用范围）。

### 4.3 `switch` 表达式 + 模式匹配

```java
// 老写法
String text;
switch (status) {
    case 0: text = "待支付"; break;
    case 1: text = "已支付"; break;
    default: text = "未知";
}

// Java 14+ 箭头写法（不会贯穿，不用 break）
String text = switch (status) {
    case 0 -> "待支付";
    case 1 -> "已支付";
    case 4 -> "已退票";
    default -> "未知";
};
```

Java 17 还支持 `instanceof` 模式匹配：

```java
if (obj instanceof String s) {      // 直接声明变量，不用强转
    System.out.println(s.length());
}
```

> 你项目里前端 `pages.js` 有一句 `['待支付','已支付',...][s]`，
> 后端 Java 里对应的就是 `switch` —— 可以对比一下两种写法。

### 4.4 `text block`（多行字符串）

```java
String sql = """
        SELECT * FROM train_order
        WHERE user_id = ?
        ORDER BY create_time DESC
        """;
```

写 SQL / JSON 时很有用。你项目里 `setSql("remain = remain + " + n)` 这种拼接，用 text block 会清晰得多
（但**更要紧的是改成参数化**，见第 5 章）。

3. `switch` 箭头写法相比冒号写法，解决了什么问题？

## 第 5 章　异常：你项目里只有一个 `BusinessException`

### 5.1 现状

你只有一个自定义异常 `BusinessException`，所有业务错误都用它 + `ResultCode` 区分。

**这不算错** —— 很多团队就这么干。但有两个点你要能讲清楚：

### 5.2 受检异常 vs 非受检异常

| | 受检（`extends Exception`） | 非受检（`extends RuntimeException`） |
| --- | --- | --- |
| 编译期检查 | 必须 try 或 throws | 不强制 |
| 代表 | IO 错误、网络 | 参数错误、业务规则不满足 |
| 你项目用的 | — | `BusinessException extends RuntimeException` |

**为什么业务异常用非受检**：业务错误到处都是，如果强制 try，代码全是噪音；
而且 Spring 的 `@Transactional` 默认**只对 `RuntimeException` 回滚**，
用受检异常要显式写 `rollbackFor = Exception.class`（你项目里写了，这是对的）。

### 5.3 `try-with-resources`

```java
// 老写法：finally 里 close，容易漏、容易掩盖异常
InputStream in = null;
try {
    in = new FileInputStream(f);
    // ...
} finally {
    if (in != null) in.close();
}

// 新写法：自动关闭（要求资源实现 AutoCloseable）
try (InputStream in = new FileInputStream(f)) {
    // ...
}
```

### 5.4 重点：你 `buy()` 里的这段代码有个真实隐患

```java
} catch (RuntimeException e) {
    // 库存已经扣了，但后面（比如发MQ）失败 → 把库存还回去
    if (deducted) {
        stringRedisTemplate.opsForValue().increment(stockKey, count);
    }
    throw e;
}
```

**问题：抛异常 ≠ 操作没成功。**

发 MQ 的失败有两种：

| 情况 | 消息真的发出去了吗 | 你的回补 |
| --- | --- | --- |
| 连接就没建立 | ❌ 没发出去 | ✅ 回补正确 |
| **消息已被 Broker 接收，但 ack 没回来 / 超时** | ✅ **已经发出去了** | ❌ **回补会导致库存多加一张** |

第二种情况下会发生：

```
1. Redis 预扣 1 张（剩 9）
2. 消息发出去了，Broker 已接收
3. 网络抖动，客户端抛异常
4. 你的 catch 回补 → Redis 变回 10
5. 但消费者照样收到消息 → 订单落库 → DB 库存减到 9

结果：Redis 10 / DB 9 → 短暂"多卖一张"的窗口
```

**这不是致命 bug**（对账任务会把 Redis 收紧），但它暴露了一个认知盲区：
**"异常"表示"结果不确定"，不表示"一定失败"。**

**标准解法**（任选，难度递增）：

| 方案 | 做法 |
| --- | --- |
| ① 依赖对账 | 承认有窗口，靠对账兜底（你现在的实际情况） |
| ② 发送前落记录 | 先写 `local_message(状态=待发送)`，再发；异常时查证 |
| ③ 事务消息 | RocketMQ 的事务消息（RabbitMQ 不直接支持） |

> 面试时这么说最加分：**"我知道这里有个不确定窗口，目前靠对账兜底，彻底解决要本地消息表。"**
> 这比"我觉得没问题"强一百倍。

### 5.5 异常体系怎么设计（如果要做大）

```
RuntimeException
 └── KangRailException（基础）
      ├── BusinessException（业务规则不满足，前端可展示 message）
      ├── AuthException（401/403）
      └── SystemException（内部错误，不暴露细节给前端）
```

原则：**能给用户看的（业务）和不能给用户看的（系统）要分开**，
否则 `e.getMessage()` 直接返回给前端，会泄露 SQL、堆栈、内部地址。
