## 第 1 章　ThreadLocal：你已经在用了，但可能不知道为什么

### 1.1 先看你的代码

`framework/.../security/UserContext.java` 大致长这样：

```java
public class UserContext {
    private static final ThreadLocal<Long> HOLDER = new ThreadLocal<>();

    public static void set(Long userId) { HOLDER.set(userId); }
    public static Long get() { return HOLDER.get(); }
    public static void clear() { HOLDER.remove(); }
}
```

`JwtInterceptor` 里：`preHandle` 调 `UserContext.set(userId)`，`afterCompletion` 调 `clear()`。

**为什么能这样用？** 因为 `ThreadLocal` 的每个值，是**挂在当前线程身上的**。

### 1.2 为什么"挂在当前线程身上"能解决问题

Tomcat 处理请求的模式是：**200 个 worker 线程，服务上万个请求**。

```
请求A（张三, userId=4） ──► 线程 T-1  → UserContext.set(4)
请求B（李四, userId=7） ──► 线程 T-2  → UserContext.set(7)
请求C（王五, userId=9） ──► 线程 T-1  → UserContext.set(9)   ← T-1 被复用了
```

因为值挂在 T-1 自己身上，请求 C 覆盖掉就行，不会读到张三的 4。
**如果用 `static Long currentUserId`，B 和 C 会互相覆盖 —— 这就是线程安全问题。**

### 1.3 那为什么必须 `clear()`？不清会怎样

假设某个接口**不需要登录**（比如 `/api/pay/callback`，在拦截器的放行名单里），
`preHandle` 里就直接 `return true` 了，**没有 set**。

```
T-1 处理请求A（张三，已登录）→ set(4)
T-1 处理完，但如果没 clear → value 还是 4
T-1 处理请求B（支付回调，免登录）→ 业务代码里调 UserContext.get() → 读到 4！
```

**后果：一个不需要登录的接口，拿到了上一个用户的身份。** 轻则写错数据归属，重则越权。

你项目里在 `afterCompletion` 里 clear 了 —— 这是对的。**但要能讲出"不清会怎样"，这才是理解。**

### 1.4 原理：值到底存在哪

```
Thread 对象
 ├── threadLocals  (ThreadLocalMap)
 │     └── Entry[] table
 │           ├── Entry: key = 弱引用(ThreadLocal对象), value = 强引用(你的值)
 │           └── Entry: ...
 └── inheritableThreadLocals
```

关键点：

| 事实 | 含义 |
| --- | --- |
| 值是存在 **Thread** 里的，不是存在 ThreadLocal 里 | ThreadLocal 只是个"钥匙" |
| Entry 的 key 是**弱引用** | ThreadLocal 对象没人用了会被 GC 回收 |
| Entry 的 value 是**强引用** | 只要线程活着，value 就不会被回收 |

**内存泄漏是怎么发生的**：

1. 某个 `ThreadLocal` 对象不再被引用 → 被 GC → Entry 的 key 变成 `null`
2. 但 value 还被 Entry 强引用着
3. Entry 又被 Thread 的 ThreadLocalMap 引用着
4. **线程不死（线程池里的线程永远不死）→ 这个 value 永远回收不掉**

所以 `remove()` 不只是"清值"，是**断掉引用链**。

### 1.5 一个能直接连到你项目的现象

你项目里日志格式是 `[%X{traceId}]`，而 `MDC` 底层就是 `ThreadLocal`。

还记得实测结果吗：

```
[http-nio-8080-exec-102] [3438ada6] 预扣库存成功 ...   ← 请求线程，有 traceId
[RabbitListenerContainer#0-1] []     订单落库成功 ...   ← MQ 消费线程，空的
```

**为什么消费者线程里 traceId 是空的？** 因为 ThreadLocal 不跨线程传递。
主线程 set 的值，消费者线程（另一个线程）根本看不到。

> 想解决：要么在消息体里带上 traceId，消费者收到后手动 `MDC.put`；要么用 `TransmittableThreadLocal`（阿里开源的 TTL）。
> **这个点面试讲出来非常加分**，因为它是"你踩过并想清楚了"的证据。

## 第 2 章　线程池：从"你的定时任务只有一个线程"说起

### 2.1 现象

你项目里用 `@Scheduled` 做对账（`StockReconcileTask`，每 5 分钟一次）。

假设你以后加了三个定时任务：

```java
@Scheduled(fixedDelay = 300000) public void reconcile() { ... }   // 对账
@Scheduled(fixedDelay = 60000)  public void preheat()   { ... }   // 预热
@Scheduled(fixedDelay = 30000)  public void cleanLog()  { ... }   // 清理
```

**它们默认是同一个线程串行跑的。** 如果 `reconcile()` 因为数据库慢卡了 40 秒，
`preheat()` 和 `cleanLog()` 都得排队等。

原因：Spring Boot 的定时任务调度器默认 `spring.task.scheduling.pool.size = 1`。

### 2.2 线程池到底怎么工作（最容易答错的地方）

很多人以为"任务多了就开新线程，开到 max 再说"。**错。**

正确顺序（`ThreadPoolExecutor.execute`）：

```
来一个任务
   │
   ├─ 当前线程数 < corePoolSize ?  ── 是 ──► 新建核心线程执行
   │                                否
   ▼
   ├─ 队列没满 ?                   ── 是 ──► 放进队列，等空闲线程来取
   │                                否
   ▼
   ├─ 线程数 < maximumPoolSize ?   ── 是 ──► 新建非核心线程执行
   │                                否
   ▼
   └─ 触发拒绝策略
```

> **关键：先入队列，队列满了才扩容到 max。**
> 这就是为什么"用无界队列时，maximumPoolSize 永远用不上"。

### 2.3 为什么阿里规约禁止用 `Executors`

| 方法 | 隐藏的问题 |
| --- | --- |
| `newFixedThreadPool(n)` | 队列是 `LinkedBlockingQueue`（**无界**，容量 `Integer.MAX_VALUE`）→ 任务堆积 → **OOM** |
| `newSingleThreadExecutor()` | 同上 |
| `newCachedThreadPool()` | `maximumPoolSize = Integer.MAX_VALUE` → 线程数爆炸 → **OOM** |

正确做法：**手动 `new ThreadPoolExecutor(...)`，7 个参数全部显式指定。**

### 2.4 怎么写：给你的定时任务配线程池

```java
@Configuration
public class SchedulingConfig {

    @Bean
    public ThreadPoolTaskScheduler taskScheduler() {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(4);                          // 4 个定时任务可以并行
        scheduler.setThreadNamePrefix("kr-sched-");        // 出问题能一眼看出是定时任务的线程
        scheduler.setWaitForTasksToCompleteOnShutdown(true);// 关机时把正在跑的任务跑完
        scheduler.setAwaitTerminationSeconds(30);
        return scheduler;
    }
}
```

**三个参数为什么要设：**

| 参数 | 不设会怎样 |
| --- | --- |
| `poolSize` | 默认 1，任务串行，互相拖累 |
| `threadNamePrefix` | jstack 里全是 `pool-1-thread-1`，排查时不知道是谁 |
| `waitForTasksToCompleteOnShutdown` | 关机直接杀线程，对账跑到一半被中断 |

### 2.5 拒绝策略怎么选

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 不能丢任务的场景 |
| `CallerRunsPolicy` | **让提交任务的线程自己跑** | 能自然限流（上游变慢，压力回传） |
| `DiscardPolicy` | 悄悄丢掉 | 不重要（如埋点日志） |
| `DiscardOldestPolicy` | 丢掉队列里最老的 | 只要最新的 |

## 第 3 章　JMM 与 volatile：为什么一个 `while` 循环会卡死

### 3.1 现象

```java
public class Demo {
    static boolean running = true;          // 注意：没有 volatile

    public static void main(String[] args) throws Exception {
        new Thread(() -> {
            while (running) { /* 空转 */ }
            System.out.println("线程退出了");
        }).start();

        Thread.sleep(1000);
        running = false;                     // 主线程改值
        System.out.println("已把 running 改成 false");
    }
}
```

**很多机器上，这个程序会一直输出"已把 running 改成 false"，但永远不会打印"线程退出了"。**

### 3.2 为什么

两个原因叠加：

1. **CPU 缓存**：工作线程把 `running` 读进了自己的 CPU 缓存/寄存器，主线程改的是主存里的值，工作线程**看不到**（可见性问题）。
2. **JIT 优化**：编译器发现循环里 `running` 没变过，干脆把它优化成"死循环"（有序性/优化问题）。

### 3.3 Java 内存模型（JMM）的三大特性

| 特性 | 含义 | 谁保证 |
| --- | --- | --- |
| **原子性** | 一个操作不可分割 | `synchronized`、`Atomic*`、锁 |
| **可见性** | 一个线程的修改，别的线程能看见 | `volatile`、`synchronized`、`final` |
| **有序性** | 禁止指令重排到不该去的位置 | `volatile`、`synchronized` |

**`volatile` 只解决后两个，不解决原子性。**

### 3.4 反例：`volatile` 救不了 `i++`

```java
volatile int count = 0;
count++;     // 实际是三步：读 count → 加 1 → 写回
```

两个线程同时执行时：

```
T1: 读 count=0
T2: 读 count=0        ← 都读到 0
T1: 写 1
T2: 写 1              ← 覆盖，结果还是 1，丢了 1 次
```

所以计数器要用 `AtomicInteger` 或 `LongAdder`，不是 `volatile`。

### 3.5 happens-before：判断"能不能看见"的规则

不用背全部 8 条，先记住这 6 条就够用：

| 规则 | 意思 |
| --- | --- |
| 程序顺序 | 同一个线程里，前面的操作对后面的可见 |
| 监视器锁 | 解锁 happens-before 后续对同一把锁的加锁 |
| **volatile** | 对 volatile 变量的写，happens-before 后续对它的读 |
| 线程启动 | `Thread.start()` 之前的操作，对新线程可见 |
| 线程终止 | 线程里所有操作，对 `join()` 返回之后的代码可见 |
| 传递性 | A hb B，B hb C ⇒ A hb C |

## 第 4 章　CAS 与原子类

### 4.1 现象

```java
int count = 0;
// 100 个线程各加 1000 次
// 期望 100000，实际往往只有 9 万多
```

原因：`count++` 不是原子操作（读-改-写三步），并发下互相覆盖。

### 4.2 CAS 是什么

**Compare And Swap：比较并交换。** 一条 CPU 指令（`cmpxchg`），语义是：

```
if (当前值 == 期望值) {
    当前值 = 新值;
    return true;
} else {
    return false;   // 说明被别人改过了
}
```

Java 里通过 `sun.misc.Unsafe` 暴露：

```java
public final boolean compareAndSet(int expect, int update) {
    return unsafe.compareAndSwapInt(this, valueOffset, expect, update);
}
```

**`AtomicInteger.incrementAndGet()` 的本质就是一个 CAS 自旋**：

```java
do {
    int old = get();
} while (!compareAndSet(old, old + 1));   // 失败了就重试
```

**它不需要加锁** —— 因为"比较 + 交换"是一条原子指令。

### 4.3 CAS 的两个坑

| 坑 | 说明 | 解法 |
| --- | --- | --- |
| **ABA** | 值从 A→B→A，CAS 以为没变过，其实变过两次 | `AtomicStampedReference`（加版本号） |
| **自旋开销** | 并发越高，CAS 失败越多，CPU 空转越久 | `LongAdder` 分段累加 |

### 4.4 为什么 `LongAdder` 比 `AtomicLong` 快

`AtomicLong`：所有线程抢**同一个** `value` 做 CAS → 竞争激烈，大量失败重试。

`LongAdder`：内部是一个 `Cell[]` 数组，不同线程 CAS 到**不同 Cell** → 竞争被分散；
取值时把 `base + 所有 Cell` 加起来。

> 代价：`sum()` 拿到的不是强一致的瞬时值。**统计场景（QPS、计数）用它，需要精确值用 `AtomicLong`。**

## 第 5 章　synchronized 与锁升级

### 5.1 三个用法

```java
synchronized (obj) { }              // 锁对象
synchronized void method() { }      // 锁 this
static synchronized void m() { }    // 锁 Class 对象
```

### 5.2 锁存在哪：对象头

每个 Java 对象在内存里都有一个 **Mark Word**（64 位），锁的状态就记在里面：

| 状态 | Mark Word 内容 | 什么时候 |
| --- | --- | --- |
| 无锁 | hashCode + 分代年龄 | 刚创建 |
| **偏向锁** | 偏向的线程 ID | 只有一个线程反复进入 |
| **轻量级锁** | 指向栈中 Lock Record 的指针 | 有第二个线程来竞争（短暂自旋） |
| **重量级锁** | 指向 monitor（ObjectMonitor）的指针 | 自旋失败，进入阻塞队列 |

**升级路径是单向的**：偏向 → 轻量 → 重量，**不会降级**。

> ⚠️ JDK 15 起偏向锁被废弃（JEP 374），**JDK 17 默认关闭**。
> 面试时如果你说"偏向锁"要补一句"JDK 15 之后默认禁用了"，否则显得知识没更新。

### 5.3 为什么轻量级锁要自旋

线程阻塞/唤醒需要从用户态切到内核态，开销很大。
如果锁只被占用很短时间，**自旋等一会儿**比"挂起再唤醒"更划算。

JDK 6 之后自旋是**自适应**的（根据上次成功与否决定自旋次数）。

### 5.4 synchronized vs ReentrantLock

| 维度 | synchronized | ReentrantLock |
| --- | --- | --- |
| 实现 | JVM 层面（monitor） | JDK 层面（AQS） |
| 释放 | 自动（异常也会释放） | **必须 `finally` 里 unlock** |
| 可中断 | 不能 | `lockInterruptibly()` |
| 超时 | 不能 | `tryLock(timeout)` |
| 公平锁 | 不支持 | 支持 |
| 条件变量 | 一个（wait/notify） | 多个 `Condition` |

> **你项目里 Redisson 的 `RLock` 就是基于 `ReentrantLock` 的接口设计**，
> 所以你会看到 `tryLock(waitTime, leaseTime, unit)` 和 `isHeldByCurrentThread()`。

## 第 6 章　AQS（面试超高频，一定要讲透）

### 6.1 先理解它要解决什么问题

你要实现一把锁，最基本的需求：

- 有人占着锁时，其他人**排队等**
- 占锁的人释放后，**叫醒**队列里的下一个
- 支持**可重入**（同一个线程重复加锁不死锁）

AQS（AbstractQueuedSynchronizer）就是把这套"排队 + 唤醒 + 状态"的通用逻辑**写好**，
你只要实现"怎么判断能不能拿到锁"。

### 6.2 用停车场理解 AQS

| 停车场概念 | AQS 对应 |
| --- | --- |
| 剩余车位数量 | `state`（volatile int） |
| 停车场入口的道闸 | CAS 修改 `state` |
| 车位满了之后的排队通道 | **CLH 双向队列**（存 `Node`，每个 Node 包一个线程） |
| 有人开车离开 | `release()` → 唤醒队头节点的线程 |
| 只有 1 个车位 | 独占模式（`ReentrantLock`） |
| 有 5 个车位 | 共享模式（`Semaphore`/`CountDownLatch`） |

### 6.3 三个核心部件

```java
public abstract class AbstractQueuedSynchronizer {
    private volatile int state;              // ① 状态，含义由子类定义
    private transient volatile Node head;    // ② 队列头（哨兵节点）
    private transient volatile Node tail;    // ③ 队列尾
}
```

**`state` 的含义是"由子类定义"的**，这一点必须记住：

| 实现类 | `state` 的含义 |
| --- | --- |
| `ReentrantLock` | 0=空闲，>0 = 重入次数 |
| `Semaphore` | 剩余许可数 |
| `CountDownLatch` | 剩余计数 |
| `ReentrantReadWriteLock` | 高 16 位读锁数，低 16 位写锁数 |

### 6.4 加锁的完整流程（ReentrantLock 非公平）

```
lock()
  │
  ├─ ① CAS 把 state 从 0 改成 1
  │      成功 → 把当前线程记为独占线程 → 拿到锁，返回 ✅
  │      失败 ↓
  ├─ ② 判断"是不是我自己已经持有" → 是则 state+1（重入）
  │      不是 ↓
  ├─ ③ 封装成 Node，CAS 挂到队列尾部
  │
  └─ ④ 在队列里 park() 挂起，等前一个节点唤醒
```

释放：

```
unlock()
  ├─ state - 1
  ├─ 如果 state == 0 → 清空独占线程
  └─ 唤醒 head 的下一个节点（unpark）
```

### 6.5 为什么叫"模板方法模式"

AQS 把流程写死了，把"能不能拿锁"留给子类实现：

| AQS 提供（写好的） | 子类实现（你要写的） |
| --- | --- |
| 入队、出队、park/unpark | `tryAcquire(int)` |
| `acquire` / `release` 整体流程 | `tryRelease(int)` |
| 中断处理、超时处理 | `isHeldExclusively()` |

所以你写自定义锁时，**只需要实现 `tryAcquire` 和 `tryRelease`**，排队和唤醒 AQS 全包了。

## 第 7 章　ConcurrentHashMap

### 7.1 先说 `HashMap` 并发会出什么事

| JDK 版本 | 并发问题 |
| --- | --- |
| 1.7 | 扩容用**头插法**，并发扩容可能形成**环形链表** → `get()` 死循环，CPU 100% |

### 7.2 演进

| 版本 | 方案 | 并发度 |
| --- | --- | --- |
| 1.7 | **Segment 分段锁**（继承 `ReentrantLock`），默认 16 段 | 16 |
| 1.8 | **CAS + synchronized 锁单个桶的头节点** | 桶的数量级 |

1.8 的做法：

```
put(key, value)
  ├─ 桶是空的 → CAS 直接放进去（无锁）
  ├─ 桶非空 → synchronized(桶的头节点) → 遍历链表/红黑树插入
  └─ 链表长度 ≥ 8 且容量 ≥ 64 → 转红黑树
```

**为什么锁粒度能细到"一个桶"**：因为锁的是数组下标 `i` 对应的那个链表头，
不同的桶互不影响。
