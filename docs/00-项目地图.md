## 1. 一句话说清这个项目

> **一个电影票购票系统，核心是「高并发下余票不超卖」和「异步链路的最终一致」。**

不是 CRUD：全项目 80% 的复杂度都在这两件事上。

---

## 2. 技术栈

| 层 | 技术 | 用来干什么 |
| --- | --- | --- |
| 语言 | Java 17 | — |
| 框架 | Spring Boot 2.7 | Web、IoC、事务 |
| ORM | MyBatis-Plus | 单表 CRUD、Lambda 条件构造器 |
| 数据库 | MySQL 8 | 订单、库存、影院场次的权威数据 |
| 缓存 | Redis + Spring Data Redis | 余票缓存、幂等键、订单号序列、token |
| 分布式锁 | Redisson | 按「场次+日期+票种」加锁 |
| 原子操作 | Redis Lua 脚本 | 判断 + 扣减合成一步 |
| 消息队列 | RabbitMQ | 异步落库、延时关单 |
| 前端 | 原生 JS + nginx | 页面 + 静态托管 + 反代 |
| 监控 | Actuator + MDC traceId | 健康检查、全链路日志 |

**多模块 Maven**：

```
common     常量（Redis key、MQ 队列名、错误码）
pojo       实体 / DTO / VO
framework  技术组件：JWT 拦截器、Redis、Redisson、RabbitMQ 配置、全局异常
server     业务：controller / service / mapper / mq / task
frontend   纯静态页面
```

**分层的意义**（面试会问）：`framework` 不依赖 `server`，所以换业务不用改`framework`；`pojo` 里的 VO 与 entity 分离，避免把数据库字段直接暴露给前端。

## 3. 数据模型（6 张表）

| 表 | 含义 | 关键字段 |
| --- | --- | --- |
| `cinema` | 影院 | cinema_code、cinema_name、city |
| `screening` | 场次 | screening_no、movie_name、cinema_id、hall_id、start_time、end_time |
| `hall` | 影厅 | screening_id、cinema_id、hall_no、open_time、close_time、cleanup_minutes、row_count |
| `screening_seat` | **票种库存（热点表）** | screening_id、show_date、ticket_type、total、remain、price、version |
| `movie_order` | 订单 | order_no、user_id、screening_id、show_date、cinema_id、hall_id、ticket_type、ticket_count、total_amount、status、pay_expire_time |
| `movie_order_item` | 订单明细 | order_id、passenger_name、id_card_no、seat_no、status |

外加 `stock_release_log`（库存释放幂等日志）、`sys_user` / `sys_role` / `sys_user_role`。

**三个必须记住的设计点**：

1. **余票存在 `screening_seat`，维度是「场次 + 放映日期 + 票种」** —— 这决定了锁的粒度。
2. **`movie_order_item.seat_no` 预留但未使用** —— 真选座还没做，这点面试要主动说。
3. **`stock_release_log.order_no` 是唯一键** —— 防 MQ 重投导致库存多加（详见 01 第 8 节）。

## 4. 一次购票的完整链路

```
① 用户点"购票"
   POST /api/ticket/buy   { screeningId, showDate, ticketType, ticketCount, passengerName, idCardNo }
        │
        ├─[JwtInterceptor] 校验 token（Redis: user:token:{userId}）→ UserContext.set(userId)
        │                                     ↘ MDC.put(traceId) 打日志
        │
        ├─[幂等] SETNX order:dup:{userId}:{screeningId}:{showDate}  TTL 30s
        │        失败 → 1002 请勿重复下单
        │
        ├─[加锁] Redisson tryLock(screening:lock:{screeningId}:{showDate}:{ticketType}, 等3s, 租约10s)
        │        失败 → 1000 当前购票人数较多
        │
        ├─[预扣] Lua: if remain >= n then remain-=n else return -1  （key: screening:stock:...）
        │        -2 → 未放票；-1 → 余票不足
        │
        ├─[订单号] INCR order:seq:{yyyyMMdd} → KR20261101000001
        │
        ├─[发MQ]  movie.order.create.queue  （消息体：orderNo/userId/screeningId/showDate/ticketType/count/乘客）
        │
        └─ 返回 orderNo，状态 0 待支付
                │
                ▼
       OrderCreateConsumer（另一个线程）
        ├─ 按 orderNo 查重（幂等）
        ├─ 插 movie_order + movie_order_item
        ├─ UPDATE screening_seat SET remain = remain - n WHERE remain >= n   ← DB 也扣，防缓存过期后"库存复活"
        └─ 发延时消息 movie.order.timeout.queue（TTL 30 分钟 → 死信 → 消费端关单）
```

**关键点：接口里只做「Redis 预扣 + 发消息」，三次 DB 写全挪到消费者。**
这就是接口能压到毫秒级的原因，也是"最终一致"的来源。

## 5. Redis Key 一览

| Key | 类型 | TTL | 用途 |
| --- | --- | --- | --- |
| `screening:stock:{id}:{date}:{type}` | String（数字） | **600s + 随机 0~60s** | 余票，读缓存 / Lua 扣减 |
| 同上 `+ #rebuild` | String | 10s | 互斥重建锁（防击穿） |
| 同上，值为 `EMPTY` | String | **60s** | 空值缓存（防穿透） |
| `screening:lock:{id}:{date}:{type}` | Redisson Hash | 租约 10s | 分布式锁 |
| `order:dup:{userId}:{screeningId}:{date}` | String | **30s** | 下单幂等 |
| `order:seq:{yyyyMMdd}` | String（自增） | 无 | 每日订单号序列 |
| `user:token:{userId}` | String | 与 JWT 一致 | 登录态（支持踢下线） |

**为什么余票 TTL 要加随机数、空值 TTL 只有 60s**：见 01 第 2 节。

## 6. MQ 队列一览

| 队列 | 作用 | 谁消费 |
| --- | --- | --- |
| `movie.order.create.queue` | 下单 → 异步落库 | `OrderCreateConsumer` |
| `movie.order.delay.queue` | 延时队列（TTL 30 分钟，**无消费者**） | 到期变死信 |
| `movie.order.timeout.queue` | 死信转入，执行关单 | `orderTimeoutConsumer` |
| `movie.stock.release.queue` | 释放库存（取消/退票/超时） | `StockReleaseConsumer` |

**延时关单的实现**：`delay` 队列不设消费者，只设 `x-message-ttl` + `x-dead-letter-routing-key`，
消息躺满 30 分钟自动变成死信转发到 `timeout` 队列。**不用轮询数据库扫超时订单。**

## 9. 自我介绍话术

**30 秒版**：

> 我做过一个电影票购票系统，核心是解决高并发下的余票扣减和异步链路的最终一致。
> 技术栈是 Spring Boot + MyBatis-Plus + Redis + Redisson + RabbitMQ。
> 压测过：12 个人抢 10 张票账目能对平，1000 次余票查询只有 4 次打到数据库。

**被问"详细说说"时的 2 分钟版**（按这个顺序讲）：

1. **背景**：票务是"读多写少 + 库存强一致"，查余票远多于下单，但一超卖就是事故。
2. **难点**：① 并发扣减不能超卖 ② 余票查询扛不住库 ③ 下单要写三张表，接口慢。
3. **做法**：① 四层防超卖 ② 缓存三兄弟 ③ MQ 异步落库 + 延时关单。
4. **结果**：账平、1000 次查询 4 次落库、20 并发 1430 QPS。

> 讲完这四段，面试官自然会挑一个点往下问 —— 那正是 02 篇准备的内容。
