## 1. 这是个什么项目

> **一个电影票购票系统。核心不是"能买票"，而是"一千个人抢一百张票的时候，账还算得对"。**

常规的 CRUD 后台，难点在功能覆盖；票务系统的难点在**并发**和**一致性**：

- 同一场次的票，几百人同时点"购买"，**一张都不能多卖**；
- 余票查询的流量是下单的几十倍，**不能全压到数据库**；
- 下单要写订单、写明细、扣库存三张表，**接口必须足够快**；
- 下单成功但支付超时，**票要能自己回到池子里**；
- 服务挂了、MQ 重投了、缓存过期了，**账目最后还得是平的**。

这个项目就是围绕这几件事做的。业务功能（影院、场次、选票、下单、支付、退票、管理后台）完整可用，但代码的重心明显偏向上面那五条。

**技术栈一句话**：Spring Boot 2.7 + MyBatis-Plus + MySQL 8 + Redis + Redisson + RabbitMQ，前端 Vue 3 + Element Plus，nginx 反向代理 + 双实例。

## 3. 技术选型

| 层 | 选型 | 为什么是它 |
| --- | --- | --- |
| 框架 | Spring Boot 2.7.18 / Java 17 | 生态成熟，拦截器、事务、AOP 都现成 |
| ORM | MyBatis-Plus | 单表 CRUD 免写 SQL，复杂条件用 Lambda 构造器；比 JPA 更好控制实际执行的 SQL |
| 数据库 | MySQL 8 / InnoDB | 订单和库存的权威数据，事务 + 行锁 + 唯一键是最后一道防线 |
| 缓存 | Spring Cache + StringRedisTemplate | 注解缓存用于影院/场次这类低频变更数据；余票这种要精确控制的走原生 API |
| 分布式锁 | Redisson | 自带看门狗续租、可重入，比自己 `SETNX` 再写续租逻辑可靠 |
| 原子扣减 | Redis Lua | 判断余票和扣减必须是一步，否则中间会被插队 |
| 消息队列 | RabbitMQ | 下单异步落库、TTL + 死信做延时关单 |
| 对象存储 | 阿里云 OSS | 图片放 OSS 不占应用服务器磁盘；URL 直接入库，`<img>` 直接引用。上传接口做了「扩展名 + 文件头魔数」双重校验，防止把木马改名为 .jpg 传上来 |
| 认证 | JWT + 拦截器 + Redis | 无状态，天然支持多实例；token 存 Redis 才能"踢下线" |
| 前端 | Vue 3 + Vite + Element Plus + axios | 组合式 API，构建快，组件够用 |
| 网关 | nginx 1.30 | 静态资源托管 + 反向代理 + 双实例负载均衡 |
| 监控 | Actuator + MDC traceId | 健康检查；一次请求的所有日志用 traceId 串起来 |

## 4. 系统架构

### 4.1 代码分层（Maven 多模块）

```
common      常量与错误码：Redis Key、MQ 队列名、订单状态、缓存参数
pojo        数据对象：entity（表映射）/ dto（入参）/ vo（出参）
framework   技术组件：JWT 拦截器、Redisson、RabbitMQ、Cache、Lua、OSS 上传、全局异常、traceId
server      业务实现：controller / service / mapper / mq / task
frontend-vue  Vue 3 前端工程
```

拆模块的意义在依赖方向：**`framework` 不依赖 `server`**，所以换一套业务逻辑，限流、鉴权、异常处理这些组件可以整包拿走。`pojo` 里 entity 和 vo 分开，数据库字段不会直接漏给前端。

### 4.2 一个请求穿过什么

```
浏览器
  │
  ▼
nginx :80 / :200
  ├─ /assets/*  → 静态资源（强缓存 7 天）
  ├─ /index.html → 不缓存（避免发版后白屏）
  └─ /api/*     → upstream 轮询
                    ├─ 8080  node-A ─┐
                    └─ 8081  node-B ─┤
                                      ▼
                          JwtInterceptor（校验 token，写 UserContext + traceId）
                                      ▼
                          AdminInterceptor（仅 /api/admin/**，非 ADMIN 抛 403）
                                      ▼
                          Controller → Service → Mapper
                                      ▼
                     MySQL / Redis / RabbitMQ（三个实例共享）
```

两个拦截器的顺序不能反：`AdminInterceptor` 要判断角色，前提是 `JwtInterceptor` 已经把用户放进 ThreadLocal。

### 4.3 部署形态

单机开发时一个实例就够；要验证集群，同一个 jar 起两个端口，nginx 轮询。**代码不需要任何改动**——锁、缓存、幂等键、token、布隆全在 Redis 里，请求落到哪台机器都一样。

## 5. 数据模型

10 张表，核心是中间那张 `screening_seat`。

```
cinema（影院）
   └─ hall（影厅）
        └─ screening（场次：放什么电影、几点、在哪个厅）
             └─ screening_seat（票种库存：某场次 + 某天 + 某票种，还剩几张）★热点
                  └─ movie_order（订单）
                       ├─ movie_order_item（观影人明细）
                       └─ stock_release_log（库存释放幂等日志）

sys_user / sys_role / sys_user_role（登录与角色）
```

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `cinema` | cinema_code（唯一）、cinema_name、city、logo_url | 影院；`logo_url` 存 OSS 完整 URL |
| `hall` | screening_id、hall_no、row_count | 影厅，唯一键 `(screening_id, hall_no)` |
| `screening` | screening_no（唯一）、movie_name、poster_url、start_time | 场次；`poster_url` 存 OSS 海报 |
| `screening_seat` | **screening_id + show_date + ticket_type（联合唯一）**、total、remain、price、version | 票种库存，唯一键决定了锁的粒度 |
| `movie_order` | order_no（唯一）、user_id、status、pay_expire_time | 订单 |
| `movie_order_item` | order_id、passenger_name、seat_no | 明细；`seat_no` 预留，真选座未做 |
| `stock_release_log` | order_no（**唯一**）、reason | 库存释放幂等，挡住 MQ 重复投递 |

三个必须记住的设计点：

1. **余票的维度是「场次 + 放映日期 + 票种」**，不是「场次」。所以锁是 `screening:lock:{id}:{date}:{type}`，同场次不同日期、不同票种互不阻塞，锁粒度刚好等于一行库存。
2. **`screening_seat.version` 是乐观锁字段**，配合 MyBatis-Plus 的 `@Version`，管理端改库存时不会覆盖别人的修改。
3. **`stock_release_log.order_no` 是唯一键**，MQ 至少投递一次，这个键保证库存只加一次。

## 6. 一次下单发生了什么

```
POST /api/ticket/buy { screeningId, showDate, ticketType, ticketCount, 观影人 }

① JwtInterceptor   校验 JWT + Redis 里的 token 是否一致（登出/被顶号立即失效）
                    MDC.put(traceId)，这条链路后续日志都带同一个 traceId
② 幂等键             SETNX order:dup:{userId}:{screeningId}:{date}  TTL 30s
                    已存在 → 1002「请勿重复下单」
③ 分布式锁           Redisson tryLock(screening:lock:{id}:{date}:{type}, 等 3s, 租约 10s)
                    抢不到 → 「当前购票人数较多，请稍后重试」
④ Lua 原子预扣       if remain >= n then remain -= n else return -1
                    -2 未放票 / -1 余票不足
⑤ 订单号             INCR order:seq:{yyyyMMdd} → MT20261101000001
⑥ 发 MQ              movie.order.create.queue（只发消息，不写库）
⑦ 返回               订单号 + 状态 0 待支付，全程毫秒级

           ↓ 另一个线程

OrderCreateConsumer
  ├─ 按 orderNo 查重（幂等，MQ 可能重投）
  ├─ 查场次、算金额，插 movie_order + movie_order_item
  ├─ UPDATE screening_seat SET remain = remain - n WHERE remain >= n
  │    （DB 也必须扣！否则缓存 TTL 到期后从 DB 重建，库存会"复活"）
  └─ 发延时消息 movie.order.delay.queue（TTL 30 分钟）

           ↓ 30 分钟后

延时队列到期 → 死信转发 → movie.order.timeout.queue
  └─ 订单仍是待支付 → 置为已取消 → 发 movie.stock.release.queue
       └─ 插 stock_release_log（order_no 唯一键防重）→ DB 回补 + Redis 回补
```

**这套链路的关键取舍**：接口里只做「Redis 预扣 + 发消息」，三次数据库写全部挪到消费者。

- 好处：下单接口不受数据库写入速度拖累，流量高峰被 MQ 削平；
- 代价：**下单返回成功 ≠ 订单已入库**，订单真正落库要等消费者。用户立刻点"我的订单"有可能查不到，靠对账任务和重试兜底。这是一个明确的最终一致模型，不是 bug。

## 7. 六个技术难点与解法

### 7.1 防超卖：四层，一层都不能少

| 层 | 手段 | 挡住什么 |
| --- | --- | --- |
| 1 | 幂等键 `order:dup:{userId}:{screeningId}:{date}`，SETNX + 30s | 用户手抖连点两次、网络重试 |
| 2 | Redisson 锁 `screening:lock:{id}:{date}:{type}` | 同一行库存的并发修改，跨 JVM 也互斥 |
| 3 | Redis Lua 脚本 | 判断和扣减之间的插队（关键：原子性） |
| 4 | `UPDATE ... WHERE remain >= n` | 前三层都失效时的最后一道，DB 层面绝不扣成负数 |

少任何一层都会出问题：只有锁没有 Lua，锁超时后仍可能超卖；只有 Lua 没有幂等键，同一用户会下出多单。

**实测**：12 个用户同时抢 10 张票，请求分散在两个 JVM 上，成功 10 单，DB 余票 0，Redis 余票 0，订单号无重复。

### 7.2 缓存三兄弟

余票查询是典型读多写少，但缓存用不好会带来三个新问题：

| 问题 | 场景 | 解法 | 参数 |
| --- | --- | --- | --- |
| 穿透 | 查一个根本不存在的场次，每次都打库 | 空值也缓存，值写 `EMPTY` | 60s |
| 击穿 | 热点 key 恰好过期，瞬间全部涌向 DB | 互斥重建锁 `{key}#rebuild`，抢不到的自旋读缓存 | 10s |
| 雪崩 | 一批 key 同时过期 | TTL 加随机抖动 | 600s + random(0~60)s |

外加**布隆过滤器**做最前置的闸门（见 7.3）。

**实测**：缓存预热后连查 3000 次余票，MySQL 一次都没被打到；关掉任意一招，同样的查询会成倍落到数据库。

### 7.3 布隆过滤器：把"肯定不存在"挡在最前面

防穿透用空值缓存够用，但每个不存在的组合都会在 Redis 里留一个 `EMPTY`（60s），被恶意构造参数时内存会被撑爆。所以在缓存之前加一层布隆：

- **放在哪**：`queryRemain` 第一行，`contains(screeningId + ":" + date + ":" + ticketType)` 为 false 直接返回 0，不进缓存也不进 DB；
- **怎么建**：Redisson 的 `RBloomFilter`，100 万容量 / 1% 误判率，底层约 1.14 MB、7 个哈希函数，全集群共用一个 key；
- **怎么填**：管理端放票时 `add()`，启动时 `BloomFilterWarmUp` 扫 `screening_seat` 全量补登记。

两个必须知道的限制：

1. **布隆不能删元素**。删场次/删库存后，对应的位还在，会残留"可能存在"的误判——这些请求会穿到缓存和 DB，但结果正确（查不到就是 0），只是白跑一趟，可以接受。
2. **误判方向只有一个**：说"不存在"一定不存在，说"可能存在"不一定存在。所以它只能用来挡，不能用来判存在。

### 7.4 异步链路与最终一致

- **异步落库**：下单只发消息，订单落库交给消费者，接口从"三次 DB 写"变成"一次 Redis 扣减 + 一次 MQ 发送"；
- **延时关单**：`movie.order.delay.queue` 故意**不设消费者**，只配 `x-message-ttl` + `x-dead-letter-routing-key`，消息躺满 30 分钟自动变死信转发到 timeout 队列。不写定时任务扫表；
- **释放幂等**：`stock_release_log.order_no` 唯一键，重复消费第一次插不进去就直接返回，库存不会被加两次。

### 7.5 订单状态机

```
0 待支付 ──支付──► 1 已支付 ──退票──► 4 已退票
   │                   │
   │取消/超时          │出票（未实现）
   ▼                   ▼
 2 已取消            3 已出票
```

所有流转都用**带源状态条件的 UPDATE + 判断影响行数**：

```sql
UPDATE movie_order SET status = 1
WHERE order_no = ? AND status = 0     -- 只有待支付才能变已支付
```

影响行数 0 就说明状态已经变了（重复回调、已取消），直接幂等返回。这样避免了"先查后改"的并发窗口。支付回调连点十次也只有一次生效。

### 7.6 集群与故障转移

两个实例共享同一套中间件，nginx 轮询：

```nginx
upstream movie_backend {
    server 127.0.0.1:8080 max_fails=2 fail_timeout=10s;
    server 127.0.0.1:8081 max_fails=2 fail_timeout=10s;
    keepalive 32;
}
```

一致性不靠"粘性会话"，靠**状态全在共享存储里**：

| 状态 | 存在哪 | 带来的能力 |
| --- | --- | --- |
| 分布式锁 | Redis | 跨 JVM 互斥，扣减不会各扣各的 |
| 余票 / 幂等键 / token / 布隆 | Redis | 换一台机器照样认 |
| 订单 / 库存 | MySQL | 唯一键和条件更新兜底 |

**实测**：12 人抢 10 张、请求 4:6 分到两个 JVM，账目对平；kill 掉一个节点，故障瞬间的请求被 nginx 重试到健康节点（约 1 秒），之后全部直达存活节点，用户拿到的一直是 200。

一个诚实的结论：**单机跑两个 JVM 不会提升吞吐**（实测 100 并发下单实例 4179 QPS、双实例 2678），因为抢的是同一份 CPU 和内存。集群的价值是可用性和多机扩展，不是单机提速。

## 8. 工程实践

这些不是业务难点，但是"能上线"和"跑个 demo"的区别：

| 实践 | 做法 |
| --- | --- |
| 统一返回 | `Result<T>{code, message, data}`，业务码与 HTTP 状态分离；前端只判断 `code === 200` |
| 全局异常 | `@RestControllerAdvice` 统一兜住 `BusinessException` / 参数校验 / 未知异常，日志留堆栈，响应不外泄 |
| 链路追踪 | 拦截器生成 8 位 traceId 放进 MDC，logback 格式带上；同一次下单的所有日志可串起来 |
| 权限分层 | 登录校验和角色校验拆成两个拦截器，Controller 里不再写 `if (role != ADMIN)` |
| 缓存版本管理 | `@Cacheable` 方法的返回类型一旦改变，**必须清掉对应的 Redis key**，否则老缓存会把新代码打挂（踩过） |
| 数据库字符集 | 命令行导入必须 `--default-character-set=utf8mb4`，否则中文报 `Data too long` |
| 测试策略 | 46 个单元测试覆盖下单/取消/退票/支付/缓存/超时关单，全部 mock 中间件，不依赖环境 |

## 12. 一句话介绍（面试/答辩用）

**30 秒版**

> 我做了一个电影票购票系统，重点解决高并发下的余票扣减和异步链路的最终一致。
> 技术栈是 Spring Boot + MyBatis-Plus + Redis + Redisson + RabbitMQ，前端 Vue 3。
> 防超卖做了四层：幂等键、分布式锁、Lua 原子扣减、数据库条件更新。
> 压测过 12 个人抢 10 张票账目能对平，缓存预热后 3000 次余票查询一次都没打到数据库，
> 还起了两个实例加 nginx 验证过集群下不超卖和故障转移。

**被追问时的展开顺序**

1. **背景**：票务是读多写少 + 库存强一致，查余票远多于下单，但一超卖就是事故。
2. **难点**：① 并发扣减不能超卖 ② 余票查询扛不住库 ③ 下单写三张表接口慢 ④ 超时票要能自己回来。
3. **做法**：① 四层防超卖 ② 缓存三件套 + 布隆 ③ MQ 异步落库 ④ TTL 死信延时关单 ⑤ 唯一键做释放幂等。
4. **验证**：账目对平、缓存挡库、集群 6 项检查、故障转移 1 秒切换。
5. **反思**：下单成功不等于已入库，这是最终一致的代价；单机双实例不涨吞吐，扩容要换机器。
