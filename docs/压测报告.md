# 康轨 KangRail · 压测报告（P5）

> 本报告数据于 **2026-10-17** 在本机真实跑出（`scripts/loadtest.py`），**不是样例值**。
> 相比只看 QPS/P99，本次额外用 MySQL 的 `Com_select` 计数，**量化了"真正打到数据库的查询量"** —— 这是证明缓存三招有没有生效的关键指标。
>
> ⚠️ **重要修正**：上午首轮测试时机器上同时有多个 JVM / Maven 构建在抢资源，QPS 与延迟**明显偏悲观**；
> 下午在干净环境（只有 1 个应用实例）复测，读场景快了约一个数量级、100 并发也不再报错。
> 两轮数据都保留在 3.1 供对比 —— 这本身就是 P5-0「压测环境必须干净」最好的反面教材。

## 3. 数据表格

### 3.1 读场景（QPS / 延迟 / DB 查询量）

| 阶段 | 模式 | 并发 | 总请求 | QPS | 平均(ms) | P95(ms) | P99(ms) | 错误率 | **DB SELECT** |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 有缓存 | 20 | 400 | 168 | 114.1 | 127.7 | 131.2 | 0% | **4** |
| A | 有缓存 | 50 | 1000 | 411 | 115.5 | 135.9 | 183.1 | 0% | **4** |
| B | 无缓存（直查库） | 20 | 400 | 268 | 71.4 | 123.8 | 133.1 | 0% | **404** |
| B | 无缓存（直查库） | 50 | 1000 | 493 | 94.5 | 115.5 | 188.6 | 0% | **1004** |

> **最重要的一行**：同样是 1000 次余票查询，有缓存时只有 **4** 次落到 MySQL，没有缓存时 **1004** 次 —— 缓存挡掉了 **99.6%** 的数据库查询。

#### 3.1.1 复测（干净环境，只有 1 个应用实例）

| 并发 | 总请求 | QPS | 平均(ms) | P95(ms) | P99(ms) | 错误率 | DB SELECT |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20 | 400 | **1430** | 12.9 | 23.6 | 31.9 | 0% | — |
| 50 | 1000 | **1306** | 37.1 | 45.5 | 47.9 | 0% | **4** |
| 50（另一次） | 1000 | 1800 | 24.5 | 40.5 | 48.4 | 0% | — |
| 100 | 1000 | **1464** | 54.7 | 79.1 | 97.7 | **0%** | — |

对比上午同条件（有缓存）：20 并发 168 → **1430 QPS**，50 并发 411 → **1306~1800 QPS**，快约 **3~10 倍**；
100 并发从 83~99% 的 `URLError` 变成 **0 错误**。

**结论**：上午的瓶颈是**压测机自身**（多个 JVM 抢 CPU / 端口），不是应用。
同一份代码、同一套中间件，环境一干净性能就上来了 —— 这就是"压测机别和应用抢资源"的实际代价。
两次 50 并发相差 1306 vs 1800（约 ±30%），说明**即使干净环境也有较大波动**，绝对值只能横向对比、不要当基准。

#### 3.1.2 本地 Redis 下的缓存 A/B（缓存到底快多少）

> 环境变更：**Redis 已从公网 `43.166.0.94` 改为本机 `localhost:6379`**（`application-dev.yml`）。
> 这消除了之前"跨公网 RTT 吃掉缓存收益"的问题，终于可以公平对比了。

**测试方式**：串行发 30 次单请求（不含并发争抢），测真正的端到端延迟。

| 配置 | avg | **P50** | P95 | min | max |
| --- | ---: | ---: | ---: | ---: | ---: |
| ✅ 有缓存（本地 Redis） | 6.41ms | **4.39ms** | 20.62ms | 3.47ms | 27.67ms |
| ❌ 无缓存（直查 MySQL） | 11.92ms | **8.16ms** | 29.40ms | 6.69ms | 36.61ms |

**结论**：本地 Redis 下，**缓存让 P50 从 8.16ms 降到 4.39ms（快 1.86 倍）**，avg 同样快 1.86 倍。
这才是"缓存该有的样子" —— 之前 Redis 在公网时，一次缓存命中要付 10~100ms 的跨网往返，收益全被吃掉、甚至比本地 MySQL 还慢。

**并发对照（注意：此时瓶颈已转为压测客户端）**

| 并发 | 有缓存 | 无缓存 |
| ---: | ---: | ---: |
| 20 | 974 QPS / 19.3ms | 865 QPS / 21.1ms |
| 50 | 1035 QPS / 45.8ms | — |

20 → 50 并发 QPS 几乎不涨（974 → 1035），说明 **Python 压测客户端（GIL + urllib）先饱和了**，
此时并发数据只能反映客户端能力，**判断缓存优劣要看上面的串行延迟**。

### 3.3 全链路正确性验证（真实调用，非单测）

压测只证明"并发下账平"；这里再补一次**完整业务闭环**的真实调用，确认状态机与库存回补都对。

测试单：车次 1 / 2027-02-01 / 二等座，放票 **5** 张。

| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 1 | `admin` 放票 5 张 | 200，Redis 与 DB 余票均为 5 |
| 2 | `demo` 下单 1 张（乘客 张三 / 110101199001011234） | 200，订单 `KR20270201000001`，status=**0** |
| 3 | 查库 | 订单 status=0；明细 1 条（姓名/证件号正确落库）；DB 余票 5→**4**；Redis 5→**4** |
| 4 | 支付回调 `PAYTEST001` | 200 |
| 5 | 重复支付回调 | 200（幂等，`pay_time` 未被二次覆盖）；订单 status=**1** |
| 6 | 退票 | 200；status 1→**4**；**`travel_date` 仍为 2027-02-01（未被误改）** |
| 7 | 重复退票 | **1000「该订单不能退票」**（正确拒绝） |
| 8 | 退票后余票 | Redis 与 DB 均回到 **5** |
| 9 | `tester1` 下单 `KR20270201000002` → 取消 | 200；status 0→**2** |
| 10 | 重复取消 | **1004「订单已取消」**（正确拒绝） |
| 11 | 最终库存 | 5 / 5（全部归还） |

> 第 6 步是回归验证的重点：退票代码早期有 bug 会把 `travelDate` 当成 `updateTime` 写入，
> 导致乘车日期被改成"当前时间"。这次真实链路确认 `travel_date` 未被污染。
>
> ⚠️ 已知设计缺口（本次观察到）：下单是**异步落库**，如果下单后**立刻**取消，可能订单还没进库，
> 取消会因 `UPDATE` 影响行数为 0 而返回 1004。当前靠"用户手速"很难触发，但严格来说应让取消接口短暂重试或先落库再返回。

## 4. 缓存治理前后对比（本阶段最有价值的部分）

> ⚠️ 本节表格里的 **QPS / 延迟来自上午的噪声环境**，绝对值偏悲观，也不能与 3.1.1 的复测数据直接比；
> 但 **"DB 查询次数放大 10.8 倍"的结论是结构性的** —— 缓存命不命中只取决于有没有那层保护，不随机器负载变化，
> 所以这部分结论不受环境噪声影响。

### 4.1 防穿透：空值缓存

场景：查一个**不存在**的车次（9999），50 个请求同时打。

| 配置 | QPS | 平均(ms) | P99(ms) | **DB SELECT** |
| --- | ---: | ---: | ---: | ---: |
| ✅ 有空值缓存（`EMPTY`） | 115 | 421.9 | 428.5 | **5** |
| ❌ 关掉空值缓存 | 56 | 876.1 | 892.7 | **54** |

**结论**：关掉空值缓存后，同样 50 个请求把 DB 查询从 5 次打到 **54 次（10.8 倍）**，QPS 掉一半、延迟翻倍。
如果没有这层保护，一个"查不存在的车次"的接口就能被刷穿数据库。

### 4.2 防击穿：互斥重建

场景：**缓存刚失效的瞬间** —— 用从未查询过的冷 key，50 个并发同时未命中。

| 配置 | QPS | 平均(ms) | P99(ms) | **DB SELECT** |
| --- | ---: | ---: | ---: | ---: |
| ✅ 有互斥重建锁（`#rebuild`） | 125 | 387.0 | 392.3 | **5** |
| ❌ 关掉互斥重建 | 173 | 276.6 | 283.6 | **54** |

**结论**：关掉互斥锁后 DB 查询 5 → **54 次（10.8 倍）**。
注意这里有个**经典权衡**：关掉锁之后 QPS 反而更高（173 vs 125）、延迟更低（277 vs 387），
因为请求不用排队等重建了 —— **但代价是把压力全部转嫁给数据库**。
生产上数据库才是瓶颈，所以"用一点延迟换数据库的命"是划算的。

### 4.3 防雪崩：TTL 随机抖动

| 配置 | 现象 |
| --- | --- |
| ✅ TTL = 600s + `random(0..60)` | 同一批预热的 key 在 10~11 分钟内**错峰**失效 |
| ❌ TTL = 固定 600s | 同一批预热的 key 会在**同一秒**集体失效 → DB 瞬间抖动 |

> **这一项本次没有量化**，原因：雪崩是"批量预热 + 到点集体失效"的**长周期**现象（要等 10 分钟），
> 短时压测观察不到，需要配合 DB 监控看周期性尖峰。
> 复现方法：把 TTL 改成固定值、批量预热 100 个 key、等 10 分钟，观察 `Com_select` 是否在同一时刻出现尖峰。

### 4.4 一句话总结

| 手段 | 不做的后果（实测） | 代价 |
| --- | --- | --- |
| 空值缓存 | DB 查询 ×10.8，延迟 ×2 | 多存一个 `EMPTY` 值（60s） |
| 互斥重建 | DB 查询 ×10.8 | 未命中请求最多多等 ~250ms |
| TTL 抖动 | 到点集体失效（定性） | 无 |

## 5. 瓶颈分析与结论

### 5.1 瓶颈在哪

| 观察 | 判断 |
| --- | --- |
| 上午：无缓存反而比有缓存快（QPS 268 vs 168） | 该对比来自**噪声环境**，不足以下定论；但确实说明 **Redis 走公网（RTT 约 10~100ms）会吃掉相当一部分缓存收益**，而 MySQL 在本机只要几 ms |
| 并发 20→50，QPS 168→411，延迟基本不变 | 应用没到瓶颈，客户端/网络在限制 |
| 并发 100 时出现 83~99% `URLError`（**上午**） | 压测机与应用同机 + 同时有多个 JVM/构建抢资源 → 本机端口/TIME_WAIT 耗尽，**非业务问题**；下午干净环境复测 100 并发 **0 错误** |
| 干净环境 20 并发 1430 QPS，50 并发 1306~1800 | 应用没到瓶颈（远程 Redis 单次往返约 10ms，两个 GET 就是 20ms+）；瓶颈在客户端与网络 |
| 写场景 15 用户抢 10 张出现 5 个 `1000` | 瓶颈是 **Redisson 锁把"同车次+日期+席别"串行化**，`LOCK_WAIT_SECONDS=3` 不够 |

### 5.2 结论（可以直接讲的三条）

1. **不超卖已证明**：两档写场景（12 抢 10、15 抢 10）全部账平，余票不为负，订单数与明细数一一对应。
   `1000`（抢锁超时）和 `1001`（余票不足）都是**正常竞争失败（少卖）**，绝不会超卖。
2. **缓存的核心价值是"保护数据库"**：有缓存时 1000 次查询只打 4 次 DB（复测同样成立）。
   至于延迟，本次**不足以下"缓存更快/更慢"的定论** —— 上午噪声环境下无缓存反而更快，干净环境下有缓存已达 1430 QPS；
   两者都受 Redis 公网 RTT 影响，只有**同一环境内横向对比**才有意义。
3. **三招确实在起作用**：关掉任一招，DB 查询量立刻放大 ~10.8 倍，可量化、可复现。

### 5.3 优化建议

1. **Redis 就近部署**（同 VPC/同机），这是本环境最划算的优化 —— 当前缓存延迟被公网 RTT 吃掉。
2. **`LOCK_WAIT_SECONDS` 3 → 5~8 秒**，减少"少卖"；或把 `generateOrderNo` 移出锁，缩短锁内耗时。
3. **压测机与应用分开**，才能得到 100+ 并发的可信数据。
4. **给 DB 加监控**（`Com_select` / 连接数），把"缓存是否生效"变成可观测指标。

### 5.4 验收对照

| 检查项 | 标准 | 结果 |
| --- | --- | --- |
| 不超卖 | 成功数 + 余票 = 库存，余票不为负 | ✅ E1/E2 都平 |
| 订单落库 | 订单条数 = 成功数 | ✅ 10/10、10/10 |
| 明细落库 | 明细条数 = 订单条数 | ✅ 10/10、10/10 |
| 缓存有效 | 有缓存 vs 无缓存有明显差距 | ✅ DB 查询 4 vs 1004（复测同结论） |
| 全链路正确 | 下单→支付→退票/取消 状态与库存都对 | ✅ 见 3.3（11 步全部符合预期） |
| 三招可验证 | 关掉任一招能观察到现象 | ✅ 穿透/击穿已量化；雪崩为定性 |
| 限流（选做 5-5） | 同一用户高频被拒 | ⬜ 未做 |

## 6. 复现步骤

```bash
# 0. 启动（JDK 17+）；压测期间务必降日志级别
mvn clean package -DskipTests
java -jar server/target/server-1.0.0-SNAPSHOT.jar --server.port=8080 \
  --logging.level.com.kangcode=info \
  --mybatis-plus.configuration.log-impl=org.apache.ibatis.logging.nologging.NoLoggingImpl

# 1. 准备写场景用户（已存在会返回 1005，忽略）
for i in $(seq 1 20); do
  curl -s -X POST http://localhost:8080/api/auth/register \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"tester$i\",\"password\":\"123456\"}" > /dev/null
done

# 2. 读场景（有缓存）
python scripts/loadtest.py read --concurrency 20 --rounds 20
python scripts/loadtest.py read --concurrency 50 --rounds 20

# 3. 穿透：查不存在的车次（--train 9999；每次换 --date 保证冷 key）
python scripts/loadtest.py read --concurrency 50 --rounds 1 --train 9999 --date 2026-12-30

# 4. 击穿：冷 key + 高并发（换一个从未查过的 --date）
python scripts/loadtest.py read --concurrency 50 --rounds 1 --train 1 --date 2027-01-05

# 5. 写场景（放票是「增量」，必须用没有库存记录的日期）
python scripts/loadtest.py write --concurrency 12 --stock 10 --date 2026-12-28
python scripts/loadtest.py write --concurrency 15 --stock 10 --date 2026-12-29

# 6. 统计 DB 查询量（跑前跑后取差值）
pwsh -File .\scripts\db-query.ps1 "SHOW GLOBAL STATUS LIKE 'Com_select'"

# 7. 核对落库（等 5 秒让 MQ 消费）
pwsh -File .\scripts\db-query.ps1 "SELECT o.travel_date, COUNT(DISTINCT o.id) orders, COUNT(i.id) items FROM train_order o LEFT JOIN train_order_item i ON i.order_id=o.id WHERE o.travel_date>='2026-12-28' GROUP BY o.travel_date"
```

> ⚠️ **异步落库的"在途窗口"**：下单成功后立刻查库可能只看到部分订单（实测曾延迟约 39 秒才补齐）。
> 这是最终一致的正常表现 —— **判断即时账目要看 Redis 余票**（它与成功数严格对平）。
> 排查时看 RabbitMQ 管理台 `railway.order.create.queue` 的 `Ready / Unacked`。
