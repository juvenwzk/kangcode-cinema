# P7 一致性与测试加固

> 这份文档只讲两件事：**你的系统在什么情况下会把库存算错**，以及**为什么每种修法能修好**。
>
> 阅读顺序建议：**先看第 1 章的故事**（5 分钟），你会亲眼看到库存从 10 变成 11。
> 后面所有代码，都是为了不让这个 11 出现。

## 第 1 章　一个真实会发生的故障

### 1.1 故事：张三退票，结果多出一张票

系统里 2027-03-01 这趟车，放了 10 张票。

| # | 谁 | 做了什么 | 库存 | 订单状态 |
| --- | --- | --- | ---: | --- |
| 1 | 张三 | 下单 1 张 | 10 → **9** | — |
| 2 | 订单服务 | 订单落库成功 | 9 | 待支付(0) |
| 3 | 张三 | 想了想，取消订单 | 9 | 已取消(2) |
| 4 | 库存消费者 | 收到"释放库存"消息，库存 +1 | 9 → **10** | 已取消(2) |
| 5 | — | **消费者告诉 RabbitMQ「我处理完了」(ack)，但这个 ack 丢了** | 10 | 已取消(2) |
| 6 | RabbitMQ | 等了半天没收到 ack，认为你没处理完，**把同一条消息再投一次** | 10 | 已取消(2) |
| 7 | 库存消费者 | 又收到一次，又 +1 | 10 → **11** | 已取消(2) |

**结果：数据库里写着 11 张余票，实际只有 10 张。**

第 11 个人买到了票，但他上不了车。这就是**超卖**，是票务系统最严重的事故。

### 1.2 你现在的代码为什么会变成 11

```java
public void releaseStock(StockReleaseMessage message) {
    stringRedisTemplate.opsForValue().increment(key, message.getTicketCount());  // 每次都 +n
    trainSeatMapper.update(... .setSql("remain = remain + " + n));               // 每次都 +n
}
```

这段代码的问题是：**它只看"消息里让我加多少"，从不问"这条消息我是不是已经处理过了"。**

消息来 1 次就加 1 次，来 2 次就加 2 次。

### 1.3 你可能会想：MQ 怎么会把同一条消息投两次？

这是关键认知，必须建立：

> **RabbitMQ 保证的是「至少一次投递（at-least-once）」，不是「恰好一次（exactly-once）」。**

原因在第 2 章讲。结论先给你：**"同一条消息被处理两次"不是 bug，是这个中间件的正常行为。**
所以**每一个消费者都必须自己处理重复**，这是写 MQ 消费者的基本功，不是可选项。

## 第 2 章　为什么 MQ 一定会重投

### 2.1 因为"干活"和"报到"是两个动作

消费者处理一条消息，实际是两个独立步骤：

```
① 执行业务：库存 +1
② 告诉 Broker：「这条我处理完了，可以删了」  ← 术语叫 ack
```

Broker 只认第 ② 步。它没有别的办法知道你有没有干完活。

**只要 ① 做完、② 没送到，Broker 就会认为你还没处理，于是重投。**

### 2.2 ② 为什么会失败？

| 情况 | 具体过程 |
| --- | --- |
| 进程被 kill | 库存刚 +1，还没执行到 ack，进程没了 |
| 网络抖动 | ack 包丢了 |
| 消费者抛异常 | 代码在 ack 之前抛了异常（比如后面还有别的逻辑） |
| 你们的重试配置 | `application.yml` 里 `retry.max-attempts: 3`，前两次失败会重试 |
| 运维手动操作 | 在管理台点了 Requeue |

**这五种情况在生产环境里都会发生，而且不是小概率。**

### 2.3 所以要建立这个思维

```
         ┌─────────────────────────────────────────┐
         │  消息可能来 N 次（N ≥ 1）                │
         │  但业务效果必须只发生 1 次               │
         │                                         │
         │  这个性质叫「幂等」                      │
         └─────────────────────────────────────────┘
```

"幂等"不是个高级词，就是：**同一个操作执行 1 次和执行 3 次，结果一样。**

## 第 3 章　最直觉的修法，为什么不可行

你第一反应大概是：**"那我先查一下这张订单释放过没有，没有才加。"**

```java
// ❌ 看起来对，实际有洞
if (releaseLogMapper.selectByOrderNo(msg.getOrderNo()) == null) {   // 查
    releaseLogMapper.insert(...);                                   // 插
    // 加库存...
}
```

### 3.1 漏洞在"查"和"插"之间

消息是**并发消费**的（`rabbitmq.listener.simple.concurrency` 默认就是多个线程，而且你可能部署多个实例）：

```
时刻 T1   线程A：查 → 没有
时刻 T2   线程B：查 → 没有          ← B 在 A 插进去之前就查完了
时刻 T3   线程A：插 → 成功
时刻 T4   线程B：插 → 成功          ← 也成功了
结果：加两次
```

两个线程都"查过了，确实没有"，然后都插进去了。

这个现象有个专门的名字：**TOCTOU（Time-of-Check to Time-of-Use，检查完到使用完之间，状态变了）**。

### 3.2 那加锁行不行？

行，但要加**分布式锁**（因为可能多实例）。然后你就要处理：锁超时、锁续期、锁释放失败、Redis 挂了怎么办……

**有一个更简单、更可靠的办法：让数据库来做这件事。**

## 第 4 章　为什么唯一键能挡住重复

### 4.1 核心思路：把"判断"交给数据库

你不需要"自己判断有没有处理过"。你只要给表加一个**唯一约束**：

```sql
UNIQUE KEY uk_order_no (order_no)
```

然后代码变成：

```java
try {
    // 尝试记录"我要处理这张订单的释放"
    releaseLogMapper.insert(record);
    // 能插进去 = 我是第一个处理的 → 继续加库存
} catch (DuplicateKeyException e) {
    // 插不进去 = 之前已经有人插过了 → 说明处理过了，直接返回
    return;
}
```

### 4.2 为什么这样就一定安全？

因为"插一条带唯一键的记录"在数据库里是**一个原子动作**：

- InnoDB 插入时会在唯一索引上加锁
- 第二个插入要么**等待**，要么**直接报错** `DuplicateKeyException`
- **绝不可能两条都成功**

对比一下：

| 做法 | 并发时会发生什么 |
| --- | --- |
| 应用层"查 + 插" | 两个线程都查到"没有"，都插成功 ❌ |
| 数据库唯一键 | 第二个插入必报错，不可能都成功 ✅ |

**这就是"用约束代替判断"** —— 你把正确性交给了数据库的索引机制，而不是自己的 if 判断。

### 4.3 那为什么不用 Redis 的 `SETNX` 去重？

Redis 也能做（`setIfAbsent` 返回 true 表示第一次），也确实更快。**但它是缓存，不是账本：**

| Redis 的风险 | 后果 |
| --- | --- |
| 重启 / `FLUSHDB` | 去重记录全没了 → 重投时又加一次 |
| 设置了 TTL | 到期后记录消失 → 迟到很久的重投又能加一次 |
| 主从切换 | 可能丢最近写入 |
| 内存满了触发淘汰策略 | 记录被 LRU 淘汰 |

**"库存算错就赔钱"这种事，不能建在会过期的内存上。**

> 结论：**去重表是主防线（持久 + 唯一约束），Redis 只能当加速层。**
> 你现在的代码连主防线都没有，先补主防线。

### 4.4 唯一键用 `order_no` 还是 `(order_no, reason)`？

你原话说的是 `(order_no, reason)`。**我建议改成 `order_no` 单列**，理由：

一张订单最后只会进入一种终态（要么取消、要么退票、要么超时关单），**库存只该还一次**，跟"什么原因还的"无关。

如果用 `(order_no, reason)`：

| 情况 | 结果 |
| --- | --- |
| 同一订单先来 `CANCEL`、后来 `TIMEOUT` | 两条都能插进去 → **还是加两次** ❌ |

你可能会说"这不可能发生，因为状态机保证只有一个能成功"。**对，但那是另一个模块（状态机）的保证。**
让"库存不被多加"这种底线，依赖另一个模块的正确性，是不划算的。

用 `order_no` 单列，就等于说：**"不管什么原因，这张单只能还一次"** —— 最稳。

`reason` 还是照存，只是不参与唯一键。它的作用是**排查时能看出是超时还是用户取消**。

## 第 5 章　动手改（每一步都说清"不写会怎样"）

### 5.1 建表

```sql
CREATE TABLE IF NOT EXISTS stock_release_log (
    id           BIGINT      NOT NULL AUTO_INCREMENT,
    order_no     VARCHAR(32) NOT NULL COMMENT '订单号（唯一键，防消息重投）',
    reason       VARCHAR(16) NOT NULL COMMENT 'CANCEL / TIMEOUT / REFUND',
    ticket_count INT         NOT NULL COMMENT '本次回补的数量',
    create_time  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_no (order_no)          -- ← 整个方案的核心就这一行
) ENGINE = InnoDB COMMENT = '库存释放幂等日志';
```

> ⚠️ `scripts/db-query.ps1` 内部用的是 `executeQuery`，**执行 DDL 会报错**。
> 这条 SQL 请用 Navicat / DataGrip / MySQL 命令行执行。

**这张表存什么？** 每成功释放一次库存，就留一条记录。它有两个作用：
1. 唯一键挡住重复（主要作用）
2. 出问题时能查："这张订单的库存是什么时候、因为什么还回去的"（排查作用）

```java
    @Override

    public void releaseStock(StockReleaseMessage message) {

        try {
            StockReleaseLog record = new StockReleaseLog();

        }

        // ② 先改 DB（权威数据）
        int rows = trainSeatMapper.update(null, new LambdaUpdateWrapper<TrainSeat>()
                .eq(TrainSeat::getTrainId, message.getTrainId())
                .eq(TrainSeat::getTravelDate, message.getTravelDate())
                .eq(TrainSeat::getSeatType, message.getSeatType())
                .setSql("remain = remain + " + message.getTicketCount()));
        if (rows == 0) {
            log.warn("库存回补没找到对应库存行 orderNo={}", message.getOrderNo());
        }

        // ③ 最后回补 Redis
        String key = RedisKeyConstant.ticketStockKey(
                message.getTrainId(), message.getTravelDate().toString(), message.getSeatType());
        stringRedisTemplate.opsForValue().increment(key, message.getTicketCount());

        log.info("库存已回补 orderNo={} count={} DB影响行数={} reason={}",
                message.getOrderNo(), message.getTicketCount(), rows, message.getReason());
    }
```

### 5.4 逐段解释：每一处为什么必须这么写

#### ① 为什么是"先插日志"，而不是"先查再插"

第 3 章讲过了：查和插之间有窗口。**插日志 + 捕获唯一键异常**，把判断交给了数据库，没有窗口。

#### ② 为什么方法上要加 `@Transactional`

因为"插日志"和"改库存"必须**同生共死**。假设不加事务：

| 如果这样 | 会怎样 |
| --- | --- |
| 日志插进去了，但改库存时数据库报错 | 日志留下了 → 消息再重投时被日志挡住 → **这张票永远还不回去了（永久少票）** |
| 没加事务，日志插入成功但后续抛异常 | 同上 |

加上 `@Transactional` 之后：改库存失败 → 日志也回滚 → 消息重试时还能重新处理。**两者要么都成，要么都不成。**

#### ③ 为什么 Redis 要放最后

**因为 Redis 不参与 Spring 事务，回滚不了。**

对比两种顺序：

```
❌ Redis 放中间：
   ① 插日志（可回滚）
   ② Redis +n  ← 已经真的加上了，回滚不了
   ③ DB +n 抛异常 → 事务回滚，①②撤销

   结果：DB 没加，Redis 加了 → 两个数据源不一致

✅ Redis 放最后：
   ① 插日志（可回滚）
   ② DB +n（可回滚）
   ③ Redis +n ← 如果这里失败，前面全回滚，Redis 也没动
```

原则：**能回滚的操作放前面，不能回滚的放最后。**

#### ④ 为什么 catch 之后可以直接 `return`

因为 `DuplicateKeyException` 已经明确告诉你"这条消息处理过了"，不需要再做任何事。

但要注意一个**数据库差异**（面试常问）：

| 数据库 | 唯一键冲突后，事务还能继续吗 |
| --- | --- |
| **MySQL / InnoDB** | 能。只回滚**这一条语句**，事务还能正常提交 ✅ |
| **PostgreSQL** | 不能。整个事务变成 aborted，必须开 savepoint 才能继续 |

本项目用 MySQL，所以 catch 后 `return` 是安全的。**换库要重写这段。**

| 现象 | 原因 | 怎么处理 |
| --- | --- | --- |
| 一直报「重复消费」，但库存没加 | 上次释放其实失败了（库存行不存在），但日志已插入并提交 | 需要人工介入：删掉日志行重放；或改成"只有 `rows > 0` 才保留日志"的更严逻辑 |

## 第 6 章　第二类问题：事务回滚了，消息却已经发出去了

### 6.1 先看清事务的"时间线"

`cancel` 现在的代码：

```java
@Transactional
public void cancel(Long userId, String orderNo) {
    int rows = trainOrderMapper.update(...);        // ① 改状态：写进事务，还没生效
    ticketOrderProducer.sendStockRelease(msg);      // ② 发消息：这一步是"立即"的
}                                                   // ③ 方法结束，事务才 commit
```

**关键在于：第 ② 步不受事务保护。** 消息一旦发到 Broker，就收不回来了。

### 6.2 出问题的完整过程

| # | 发生了什么 | DB 里的订单 | 消费者那边 |
| --- | --- | --- | --- |
| 1 | `UPDATE` 执行成功（在事务里） | 内存中已改，未提交 | — |
| 2 | 发出"释放库存"消息 | 未提交 | 立刻收到，库存 +1 |
| 3 | 方法结束，commit... **失败**（死锁 / 连接断 / 磁盘满） | **回滚，还是"待支付"** | 已经在加了 |
| 4 | 结果 | 订单还在、还能支付 | 票已经还回去了 |

**用户一支付，就白拿一张票；或者更糟 —— 这张票又卖给别人，两个人抢一个座。**

### 6.3 那正确的顺序是什么

```
        想要的效果：
        commit 成功 ───► 才发消息
        commit 失败 ───► 什么都不发
```

Spring 提供了这个钩子：`TransactionSynchronizationManager`。
你注册一个回调，它会在**事务提交成功之后**才执行。

### 6.4 加一个 20 行的工具类

`framework/src/main/java/com/kangcode/framework/tx/AfterCommit.java`

```java
package com.kangcode.framework.tx;

import org.springframework.transaction.support.TransactionSynchronization;
import org.springframework.transaction.support.TransactionSynchronizationManager;

/**
 * 事务提交后再执行。
 * <p>用于「DB 改成功才发 MQ」：避免事务回滚了、消息却已经发出去。
 */
public final class AfterCommit {

    private AfterCommit() {
    }

    public static void run(Runnable action) {
        if (TransactionSynchronizationManager.isSynchronizationActive()) {
            // 有事务：挂个回调，等 commit 成功后执行
            TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    action.run();
                }
            });
        } else {
            // 没有事务上下文（比如在 MQ 消费线程里直接调用）→ 直接执行
            action.run();
        }
    }
}
```

**逐行解释为什么这么写：**

| 代码 | 为什么 |
| --- | --- |
| `isSynchronizationActive()` | 判断当前有没有事务。没有的话（比如单测里直接调、或在消费线程里），`registerSynchronization` 会抛异常，所以要分支 |
| `registerSynchronization(...)` | 把回调挂到**当前事务**上，事务结束时会通知它 |
| `afterCommit()` | 只在**提交成功**后调用；回滚时不调用（回滚走的是 `afterCompletion(status != COMMITTED)`） |
| `else { action.run(); }` | 没事务的时候就当场执行，否则消息永远发不出去 |

> `framework` 模块已经有 `spring-tx`（`mybatis-plus-boot-starter` 带进来的），不用加依赖。

以 `cancel` 为例，改完后长这样：

```java

        StockReleaseMessage msg = StockReleaseMessage.builder()
                .orderNo(orderNo)
                .trainId(order.getTrainId())
                .travelDate(order.getTravelDate())
                .seatType(order.getSeatType())
                .ticketCount(order.getTicketCount())
                .reason("CANCEL")
                .build();
        AfterCommit.run(() -> ticketOrderProducer.sendStockRelease(msg));
```

import：

```java
import com.kangcode.framework.tx.AfterCommit;
```

> **注意 `msg` 要在 lambda 外面构建好。** 一是 lambda 里只能用 effectively final 的变量；
> 二是养成"进 lambda 只带值"的习惯，能避免闭包拿到被改过的对象。

### 6.6 怎么验证"发早了"确实修好了

**做一个 30 秒的实验**：在 `cancel` 方法最后临时抛个异常，强制回滚。

```java
        // 临时插一行，验证事务边界
        if (true) { throw new RuntimeException("故意回滚"); }
```

| 改之前 | 改之后 |
| --- | --- |
| 异常抛出，事务回滚，但 `sendStockRelease` **已经调用过**（消息真的发出去了） | 异常抛出，事务回滚，`afterCommit` **不会被调用**，消息没发 |

验证完记得把这行删掉。

### 6.7 必须知道的局限：`afterCommit` 只解决一半

| 问题 | afterCommit 能解决吗 | 为什么 |
| --- | --- | --- |
| 事务回滚了，消息却发了（**发早了**） | ✅ | 回调只在 commit 后执行 |
| 事务提交了，发消息失败（**发丢了**） | ❌ **不能** | 此时事务已经提交、订单已取消，但消息没发出去 → 库存永远还不回去 |

"发丢了"的概率比"发早了"低，但一样会造成少票。

**彻底解决要上"本地消息表（outbox）"：**

```
【同一个事务里】
  ① UPDATE 订单状态
  ② INSERT local_message(status='待发送', payload='...')
  commit  ← 业务改动和"要发的消息"一起落地，不会丢

【独立的后台线程】
  ③ 扫 status='待发送' 的记录 → 发 MQ → 改成 '已发送'
  ④ 发失败就重试（指数退避），超过 N 次告警
```

这样：消息不会丢（DB 里有记录）、不会发早（同事务）、最多重复（靠第 5 章的唯一键去重）。

> **建议**：先做 `afterCommit`（20 行，解决 90% 场景），outbox 留到下一步。
> 面试时能说出"afterCommit 解决发早了，发丢了要靠本地消息表"——这比只会背概念强得多。

## 第 7 章　为什么这两种 bug，现有测试发现不了

### 7.1 Mockito 的世界里，坏事永远不会发生

你现在的测试长这样：

```java
when(orderMapper.selectOne(any())).thenReturn(null);
service.releaseStock(msg);
verify(seatMapper).update(any(), any());   // 只验证"调用过"
```

在 Mock 的世界里：

| 真实世界会发生 | Mock 里 |
| --- | --- |
| 第二次插同一 `order_no` → 报 `DuplicateKeyException` | `insert` 永远返回 1，永远不报错 ❌ |
| 事务回滚，前面的改动撤销 | 根本没有事务 ❌ |
| 消息被投第二次 | 你手动调两次，但没有任何"重投"语义 ❌ |

**所以"唯一键能挡住重复"这件事，用 Mockito 是永远测不出来的 —— 因为你把要验证的机制本身 Mock 掉了。**

### 7.2 结论：这两个修复必须用集成测试证明

集成测试 = 真的连 MySQL、真的连 Redis、真的走 MQ。
只有这样，唯一键、事务、异步才都是"真的"。

### 8.2 公共基类：解决两个实际问题

`server/src/test/java/com/kangcode/server/it/BaseIT.java`

```java
package com.kangcode.server.it;

import java.time.LocalDate;
import java.util.function.BooleanSupplier;

import static org.junit.jupiter.api.Assertions.fail;

/**
 * 集成测试公共部分。
 * <p>这些测试会真的写 dev 库，所以用「专用席别 + 远未来日期」做隔离。
 */
public abstract class BaseIT {

    /** 专用席别：避免和演示数据/其他测试撞车 */
    protected static final String SEAT = "测试座";

    /** 远未来日期：超出对账任务 14 天窗口，不会被定时任务干扰 */
    protected static final LocalDate DATE = LocalDate.now().plusDays(300);

    /**
     * 轮询等待异步结果。
     * <p>为什么不用 Thread.sleep：机器快慢不一样，固定 sleep 要么假失败、要么浪费时间。
     */
    protected static void awaitUntil(String desc, long timeoutMs, BooleanSupplier cond) {
        long end = System.currentTimeMillis() + timeoutMs;
        while (System.currentTimeMillis() < end) {
            if (cond.getAsBoolean()) {
                return;
            }
            try {
                Thread.sleep(200);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                fail("等待被中断：" + desc);
            }
        }
        fail("超时：" + desc);
    }
}
```

**两个设计都是被迫的，不是"讲究"：**

| 设计 | 不这么做会怎样 |
| --- | --- |
| 专用席别 `测试座` | 测试往 `二等座` 里插数据，会和你在页面上看到的数据混在一起，断言全乱 |
| 远未来日期（+300 天） | `StockReconcileTask` 每 5 分钟对账"今天~+14 天"，会把你造的库存改掉 |
| `awaitUntil` 轮询 | 用 `sleep(2000)` 的话，MQ 慢一点就假失败，快一点就白等 |

## 第 10 章　面试怎么讲（三句话）

> **"我的库存释放做了两层保护。**
> **第一层是幂等**：落一张 `stock_release_log`，用**订单号**做唯一键。因为 MQ 是至少一次投递，重投时靠唯一约束拦掉 —— 这里用数据库的原子约束，而不是应用层"先查再插"，避免并发窗口。
> **第二层是事务边界**：发消息改到 `afterCommit`，避免 DB 回滚了、消息却已经发出去。
> **代价是** `afterCommit` 只解决'发早了'，'发丢了'要靠本地消息表 + 定时补发 —— 这块我知道方案，但还没落地。"

为什么这三句有说服力：它证明你**知道系统会在哪里坏**，而不是只会说"熟悉 RabbitMQ"。
