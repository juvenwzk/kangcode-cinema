## 1. 先搞懂几个指标

| 指标 | 含义 | 为什么看它 |
| --- | --- | --- |
| **QPS** | 每秒处理的请求数 | 系统的吞吐能力 |
| **P99** | 99% 的请求在这个耗时以内完成 | **比平均值重要得多**。平均 50ms、P99 3s，说明有 1% 的用户在骂人 |
| 错误率 | 失败请求占比 | 压测时错误率必须接近 0，否则数据没意义 |
| CPU / 内存 | 机器负载 | 判断瓶颈在应用还是在资源 |
| MySQL 连接数 | HikariCP 池使用情况 | **连接池打满是最常见的瓶颈** |

## 2. 任务 5-0：压测前的准备

### ① 关掉 debug 日志（最重要）

`server/src/main/resources/application.yml` 里现在是：

```yaml
logging:
  level:
    com.kangcode: debug
```

`debug` 会把**每条 SQL、每个 MyBatis 参数**都打出来，压测时日志本身就是最大的瓶颈，数据完全不可信。 压测前临时改成：

```yaml
logging:
  level:
    com.kangcode: info
```

> 顺带把 MyBatis 的 SQL 打印也关掉——`application-dev.yml` 里有这一行，压测时注释掉：
> ```yaml
> mybatis-plus:
>   configuration:
>     log-impl: org.apache.ibatis.logging.stdout.StdOutImpl   # ← 压测时注释掉
> ```

### ② 确认测试用户够用（写场景要用不同用户）

```bash
# 注册 tester1..tester20；已存在会返回 1005，忽略即可
for i in $(seq 1 20); do
  curl -s -X POST http://localhost:8080/api/auth/register \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"tester$i\",\"password\":\"123456\"}" > /dev/null
done
```

> **为什么不能用同一个用户反复买**：`buy()` 里有幂等键 `order:dup:{userId}:{trainId}:{date}`，
> 同一用户 30 秒内只能下一单。 用同一用户压测，测出来的是**幂等逻辑**，不是购票性能。

### ③ 确认服务在跑

```bash
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"demo","password":"123456"}'
```

返回 `{"code":200,...}` 就说明服务正常。

> **端口是 8080**（后端直连）。 前端如果走 nginx 的 200 端口反代 `/api`，那是另一回事——
> 压测要打后端，所以统一用 8080。

## 3. 任务 5-1：准备压测工具

### 方案 A：JMeter（图形化，面试时更好展示）

只需要 5 个元件：

| 元件 | 配置要点 |
| --- | --- |
| 线程组 | 线程数 = 并发数（如 100）、Ramp-up = 1 秒、循环次数 = 10 |
| HTTP 请求默认值 | 服务器 `localhost`、端口 **8080** |
| HTTP 信息头管理器 | `Authorization: Bearer ${token}`、`Content-Type: application/json` |
| HTTP 请求（取样器） | 见 5-2 / 5-3 的两个场景 |
| 聚合报告 | 看 Average / **99% Line** / Error % |

### 方案 B：Python 脚本（推荐，本机就能跑）

**脚本已经放在 `scripts/loadtest.py`**，不用装任何东西，用项目自带的 Python 就能跑：

```bash
# 读场景：反复打余票查询，测 QPS / P99
python scripts/loadtest.py read --concurrency 100 --rounds 20

# 写场景：12 个用户并发抢 10 张票，验证不超卖
python scripts/loadtest.py write --concurrency 12 --stock 10 --date 2026-12-25
```

脚本支持这几个参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `mode` | 必填 | `read` 或 `write` |
| `--concurrency` | 100 / 12 | 并发数 |
| `--rounds` | 20 | 读场景里每个线程请求几次 |
| `--stock` | 10 | 写场景放多少张票 |
| `--date` | `2026-12-20` | 乘车日期，**必须是未来日期**；重复压测换一个就能绕开幂等键 |

> 脚本顶部写了 `TRAIN_ID`、`TRAVEL_DATE`、`SEAT_TYPE` 三个常量，按需改。
> **它用的是 Python 标准库**（`urllib` / `threading`），不需要 `pip install` 任何东西。

## 4. 任务 5-2：读场景（证明缓存有效）

```bash
python scripts/loadtest.py read --concurrency 100 --rounds 20
```

**怎么证明缓存有价值**：跑两遍——

1. **有缓存**：直接跑（第一次查库之后全部命中缓存）。
2. **清掉缓存**：先删掉余票 key，再跑：

```bash
redis-cli -h 43.166.0.94 DEL "ticket:stock:1:2026-12-20:二等座"
```

对比两遍的 QPS / P99，差值就是缓存省下来的。

> 再狠一点：把 `queryRemain` 里的缓存逻辑**整体注释掉**（直接查库），跑第三遍，就是"完全没缓存"的基线。

**实测样例**（本机跑了 20 并发 × 5 次）：

```text
读场景：并发 20，每人 5 次，总请求 100
  总耗时      : 0.83 s
  QPS         : 121
  平均耗时    : 155.29 ms
  P95 / P99   : 344.65 / 346.10 ms
  错误率      : 0.00%  []
```

> 你的数字会不一样（取决于机器和网络——**Redis 在远程，单次往返就有几十毫秒**）。
> 关键是**同一台机器上"有缓存 vs 没缓存"的对比**，绝对值意义不大。

## 5. 任务 5-3：写场景（证明不超卖）

```bash
python scripts/loadtest.py write --concurrency 12 --stock 10 --date 2026-12-25
```

**实测输出**：

```text
放票 10 张（2026-12-25）→ {'code': 200, 'message': '操作成功', 'data': 10}
拿到 12 个用户 token
========================================================
写场景：12 个用户并发抢 10 张票（2026-12-25）
  返回码分布  : {200: 9, 1000: 3}
  成功下单    : 9 次
  抢完余票    : 1
  账目核对    : 9(成功) + 1(余票) = 10(库存) → 平
  结论        : ✅ 不超卖，通过
  说明        : 3 个请求返回 1000 = 抢锁等待超时，
                属于正常竞争失败（少卖，不会超卖），不是 bug。
                想减少它可调大 TicketServiceImpl.LOCK_WAIT_SECONDS。
========================================================
```

**返回码怎么读**：

| 返回码 | 含义 | 算不算问题 |
| --- | --- | --- |
| `200` | 下单成功 | — |
| `1001` | 余票不足 | **正常**（票卖完了） |
| `1000` | 抢锁等待超时 | **正常**（竞争失败，少卖但**绝不超卖**） |
| `1002` | 重复下单 | 测试用错用户了（同一用户 30 秒内只能买一次） |

> ### 判通过的**唯一标准是"账平"**
>
> `成功数 + 最终余票 = 库存数`，且余票 **不为负**。
> —— 允许"少卖"（1000 / 1001），**绝不允许"超卖"**（成功数 > 库存数，或余票为负）。
>
> **为什么会出现 1000（少卖）**：`TicketServiceImpl.LOCK_WAIT_SECONDS` 现在是 **3 秒**。
> Redis 在远程（`43.166.0.94`），锁内要跑 Lua + 生成订单号 + 发 MQ，每次几十毫秒；
> 12 个请求串行下来就可能超过 3 秒窗口。 调大到 5~10 秒可以减少，但**等太久会让请求堆积**，要权衡。

> ⚠️ **重复压测两个坑**：
> 1. 换 `--date`（幂等键里带日期），否则同一批用户 30 秒内全部返回 1002；
> 2. **放票是增量的**（不是覆盖），想得到干净库存先重置：
>    ```powershell
>    pwsh -File .\scripts\db-query.ps1 "UPDATE train_seat SET total=0, remain=0 WHERE train_id=1 AND travel_date='2026-12-25'"
>    ```

**再验一次订单有没有真落库**（异步的，等两三秒）：

```powershell
pwsh -File .\scripts\db-query.ps1 "SELECT order_no, user_id, ticket_count, total_amount, status FROM train_order ORDER BY id DESC LIMIT 12"
```

应该看到 9 笔状态为 0（待支付）的订单，`ticket_count` 都是 1。

## 6. 任务 5-4：缓存治理对比（本阶段最有价值的一步）

把 `TicketServiceImpl.queryRemain` 里的三个手段**逐条关掉**，各跑一遍读场景，用数据说明每一招的作用：

| 改造 | 怎么关 | 预期现象 |
| --- | --- | --- |
| **关掉空值缓存**（防穿透） | 删掉 `loadFromDbAndCache` 里写 `EMPTY_VALUE` 那几行，改成直接 `return 0` | 查一个**不存在的车次**时，请求全打到 DB |
| **关掉互斥重建**（防击穿） | 去掉 `rebuildLockKey` 那段，未命中就直接 `loadFromDbAndCache` | 缓存刚过期那一瞬间，DB QPS 飙升 |
| **关掉 TTL 抖动**（防雪崩） | TTL 改成固定值（去掉 `ThreadLocalRandom` 那行） | 批量预热后到点集体失效，DB 出现周期性抖动 |

**做法**：每改一次 → 重启应用 → 跑一遍读场景 → 记数据 → 改回来。 最后整理成一张对比表放进报告。

> **关"防穿透"要换请求参数**：把 `scripts/loadtest.py` 里的 `TRAIN_ID` 临时改成 `9999`（不存在的车次），否则测不出效果。

## 7. 任务 5-5（选做）：接口限流

用 Redisson 的 `RRateLimiter` 给购票接口加限流——**每个用户每秒最多买 10 次**：

```java
import org.redisson.api.RRateLimiter;
import org.redisson.api.RateIntervalUnit;
import org.redisson.api.RateType;

// 放在 buy() 最前面（幂等校验之前）
RRateLimiter limiter = redissonClient.getRateLimiter("rate:buy:" + userId);
limiter.trySetRate(RateType.OVERALL, 10, 1, RateIntervalUnit.SECONDS);
if (!limiter.tryAcquire()) {
    throw new BusinessException(ResultCode.BUSINESS_ERROR.getCode(), "操作过于频繁，请稍后再试");
}
```

> 这三个 import 都在 `org.redisson.api` 下；`redissonClient` 就是 `TicketServiceImpl` 里**已经注入的那个**。
> 注意 key 里带 `userId`（按用户限流），否则会把所有用户一起限掉。

## 8. 验收清单

| 检查项 | 标准 |
| --- | --- |
| 不超卖 | 成功数 + 余票 = 库存数，且余票不为负 |
| 余票不变负 | 抢完余票 ≥ 0 |
| 缓存有效 | "有缓存" vs "无缓存"的 QPS 有明显差距 |
| 三招可验证 | 关掉任一招，都能观察到对应的现象 |
| 订单落库 | 抢完后订单条数 = 成功数 |
| 限流（选做） | 同一用户高频请求被拒 |
| 压测报告 | `docs/压测报告.md` 五部分齐全 |

## 9. 常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 压测 QPS 低得离谱 | 日志级别还是 `debug`，每条 SQL 都打印 | 见 5-0 ①，改成 `info` |
| 全部 401 | 没带 token（`Authorization: Bearer xxx`） | 你测的是拦截器，不是业务 |
| 全部 1002 | 同一批用户 30 秒内重复下单 | 换 `--date` 或换用户 |
| 放票报 400 | 用了历史日期 | 用未来日期 |
| 放票后库存比预期多 | 放票是**增量**不是覆盖 | 先重置该条记录的 `total/remain` |
| 一批 1000（少卖） | 抢锁等待 3 秒不够用 | 正常现象；想减少就调大 `LOCK_WAIT_SECONDS` |
| QPS 上不去、大量超时 | HikariCP 连接池打满 | 看 `spring.datasource.hikari.maximum-pool-size` 和 MySQL `max_connections` |
| 压测机和应用抢资源 | 压测脚本和应用跑同一台机器 | 数据偏悲观，有条件就分开 |
| Redis 报 `WRONGTYPE` | 余票 key 和锁 key 撞了 | 见 P2 3.4 节，`queryRemain` 必须用 `ticketStockKey` |
