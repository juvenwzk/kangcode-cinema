# 01 · 技术点详解

> 每一节都按同一个结构：**① 项目里在哪 → ② 为什么这么做 → ③ 不这么做会怎样 → ④ 面试怎么答**。
> ③ 是最容易被跳过、但最能体现"真懂"的部分，别省。

---

## 1. 请求链路：JWT + 拦截器 + ThreadLocal + traceId

### ① 代码位置

| 做什么 | 类 |
| --- | --- |
| 校验 token | `JwtInterceptor.preHandle` |
| 存当前用户 | `UserContext`（ThreadLocal） |
| 生成 traceId | `JwtInterceptor` 里 `MDC.put` |
| 日志格式 | `logback-spring.xml` 的 `[%X{traceId}]` |

### ② 为什么用拦截器而不是过滤器

- **Filter**：Servlet 容器层，拿不到 `HandlerMethod`，也不方便注入 Spring Bean
- **Interceptor**：Spring MVC 层，**本身是 Bean**，能注入 `JwtUtils` 和 `RedisTemplate`

我们需要查 Redis 校验 token 是否还有效（支持踢下线），所以必须能注入 Bean → 用拦截器。

### ③ token 为什么既验签又查 Redis

只验签名的话，用户改密码/退出登录后旧 token 仍然有效。
所以登录时把 token 写入 `user:token:{userId}`，拦截器要求**签名有效 + Redis 里存在且一致**。
退出登录 = 删这个 key → 旧 token 立刻失效。

### ④ `UserContext` 为什么必须在 `afterCompletion` 清掉

Tomcat 线程是**复用**的。不清的话，下一个请求如果没覆盖（比如免登录接口），会读到**上一个用户的 id** → 越权。

**面试答法**：
> "登录态用 JWT + Redis 双重校验，拦截器里解析出 userId 放进 ThreadLocal，日志里放 MDC traceId。
> ThreadLocal 必须在线程归还前 remove，否则线程池复用会串号，而且 Thread 强引用着 value 会导致内存泄漏。"

## 2. 缓存三兄弟（穿透 / 击穿 / 雪崩）

### ① 代码位置

`TicketServiceImpl.queryRemain` / `loadFromDbAndCache`

### ② 三种"没命中"的成因不同，解法也不同

| 问题 | 成因 | 本项目解法 | 参数 |
| --- | --- | --- | --- |
| **穿透** | 数据**根本不存在**，缓存永远不命中 | 查不到写 `EMPTY` | TTL **60s** |
| **击穿** | **一个热点 key 过期瞬间**，大量请求同时未命中 | 互斥重建锁 `{key}#rebuild` | 10s，抢不到就自旋等 5×50ms 再兜底查库 |
| **雪崩** | **一批 key 同时过期** | TTL 抖动 | `600s + random(0~60)` |

### ③ 不这么做会怎样（有实测）

50 个请求查同一个不存在的场次：

| 配置 | 打到 MySQL 的次数 |
| --- | --- |
| 有空值缓存 | **5** |
| 关掉空值缓存 | **54** |
| 有互斥重建 | **5** |
| 关掉互斥重建 | **54** |

**关掉任一招，数据库压力放大 10.8 倍。**

### ④ 为什么空值 TTL 只有 60s，正常库存 600s

- 空值代表"**临时**没有"（可能马上放票），缓存太久会**误报"没票"**；
- 正常库存要长，减少回源；加随机抖动是为了让批量放票预热出来的 key **错峰失效**。

**面试答法**：
> "三种情况区分开：穿透是数据没有，用空值缓存；击穿是一个 key 过期，用互斥重建；雪崩是一批 key 同时过期，用 TTL 加随机抖动。
> 我实测过，关掉任一招 50 个请求的库访问从 5 次涨到 54 次。"

## 3. 缓存与数据库对账

### ① 代码位置

`StockReconcileTask`，`@Scheduled(fixedDelay = 5 分钟)`

### ② 逻辑

```
每 5 分钟，扫「今天 ~ +14 天」的库存行：
    Redis 值 > DB 值  → 收紧 Redis（说明有"预扣了但没落库"的幽灵单）
    Redis 值 < DB 值  → 视为"有预扣在途"，不动
    Redis 不存在      → 从 DB 重建
```

### ③ 为什么必须有对账

Redis 和 MySQL 两个数据源，中间还有 MQ 异步，**不可能时刻一致**。
对账是最后一道兜底：把"不该多出来的库存"收回去。

### ④ 对账任务本身的两个坑（面试加分）

1. **多实例会重复执行** —— 目前没加分布式锁，部署两个实例会跑两遍（结果幂等所以不出错，但浪费资源）。正确做法是 `Redisson tryLock` 包住。
2. **只收紧不放宽** —— 因为"Redis 小于 DB"可能是正常的在途状态，放宽会超卖。

## 4. Redis Lua 原子预扣

### ① 代码位置

`LuaScriptConfig` 里的 `DefaultRedisScript<Long> stockDeductScript`，在 `TicketServiceImpl.buy` 调用。

### ② 脚本做了什么

```lua
local stock = redis.call('get', KEYS[1])
if not stock then return -2 end          -- 还没放票
if tonumber(stock) < tonumber(ARGV[1]) then return -1 end   -- 余票不足
return redis.call('decrby', KEYS[1], ARGV[1])               -- 扣减并返回剩余
```

### ③ 为什么不能直接 `DECR`

`DECR` 会把余票减成负数 —— 它不判断够不够。
"先 GET 判断再 DECR" 是两条命令，中间可能被别的请求插进来（并发下就超卖了）。

**Lua 脚本在 Redis 里是原子执行的**（Redis 单线程跑脚本，脚本期间不插入其他命令），
所以「判断 + 扣减」必须写在一个脚本里。

### ④ 返回值约定

`-2` = key 不存在（未放票），`-1` = 余票不足，`>= 0` = 扣减后的余票。
调用方根据返回值抛不同错误码，前端提示才准确。

**面试答法**：
> "扣减用 Lua 脚本，把'判断够不够'和'扣减'合成一个原子操作，避免 GET 和 DECR 之间的并发窗口，也顺带解决了减成负数的问题。"

## 5. Redisson 分布式锁

### ① 代码位置

`TicketServiceImpl.buy`：

```java
RLock lock = redissonClient.getLock("screening:lock:{screeningId}:{showDate}:{ticketType}");
locked = lock.tryLock(3, 10, TimeUnit.SECONDS);   // 等 3 秒，租约 10 秒
...
finally { if (locked && lock.isHeldByCurrentThread()) lock.unlock(); }
```

### ② 为什么需要分布式锁

`DECR` 是原子的，为什么还要锁？因为临界区不止扣减：

```
读库存(Lua) → 生成订单号(Redis INCR) → 发 MQ
```

这三步要保证"同一库存行"串行，否则会出现：**扣了库存但订单号生成失败**这类中间态。
锁保证临界区完整执行。

### ③ 锁粒度为什么是「场次 + 日期 + 票种」

**一行库存 = 一把锁**。太粗（全局锁）会让不同场次互相阻塞；太细（用户级）防不住超卖。

### ④ 关键细节：`leaseTime` 传了，看门狗就不生效

Redisson 只有**不指定** `leaseTime` 时才启用看门狗（默认 30s，每 10s 续期）。
本项目的 `tryLock(3, 10, SECONDS)` **显式传了租约**，所以锁到期就释放，**不会续期**。

这是取舍：

| 方案 | 好处 | 风险 |
| --- | --- | --- |
| 不传 leaseTime（看门狗） | 业务跑多久锁持多久 | 进程被 kill 要等 30s 才释放 |
| **传 10s（本项目）** | 不会死锁 | 临界区超过 10s 会提前释放 |

本项目临界区只有 Redis 操作，毫秒级，10 秒足够。

### ⑤ 抢锁等 3 秒没等到怎么办

抛 `1000 当前购票人数较多`，让用户重试。**这是"少卖不超卖"的主动选择** —— 宁可拒掉，也不让请求在锁上堆积把线程池打满。

**面试答法**：
> "用 Redisson 是因为 SETNX 自己实现有三个坑：加锁和设过期非原子、释放不校验持有者会误删别人的锁、不可重入。
> 我显式传了 10 秒租约，所以没有走看门狗，这是为了防死锁的取舍。"

## 6. 下单幂等键

### ① 代码位置

`TicketServiceImpl.buy` 第一行：

```java
String dupKey = "order:dup:{userId}:{screeningId}:{showDate}";
Boolean first = redisTemplate.opsForValue().setIfAbsent(dupKey, "1", 30, SECONDS);
if (!Boolean.TRUE.equals(first)) throw new BusinessException(ORDER_REPEATED);  // 1002
```

### ② 为什么在锁外面做

幂等键的目的是"**同一用户 30 秒内只能下一单**"，属于"用户行为"维度，比库存锁更粗。
放在锁外面能在进临界区之前就挡掉，减少锁竞争。

### ③ 为什么是 30 秒

覆盖"用户手抖点两次"和"网络超时后重试"的窗口。太短挡不住重复提交，太长会误伤"真的想买两张"的场景（那种应该一次买 2 张）。

### ④ 注意：幂等键只在 Redis，挂了会失效

严格场景应该用 DB 唯一键兜底。本项目的兜底是"订单号唯一索引"——但订单号每次新生成，挡不住重复下单。
**这是已知短板，面试可说"幂等键只做了 Redis 层，没落库"。**

## 7. MQ 异步落库

### ① 代码位置

- 生产：`TicketOrderProducer.sendOrderCreate`
- 消费：`OrderCreateConsumer`

### ② 为什么要异步

下单要写三张表：`movie_order`、`movie_order_item`、`screening_seat`（扣 DB 库存）。
同步做的话接口 RT 会被 DB 行锁拖长。异步后接口只做"Redis 预扣 + 发消息"，毫秒级返回。

### ③ 代价：最终一致

用户看到"下单成功"时，订单还没落库。
**实测过一次：5 条订单延迟约 39 秒才落库**（当时机器负载高）。

所以前端下单后立刻查订单可能查不到 —— 这不是 bug，是最终一致的表现。

### ④ 消费者里的幂等

`OrderCreateConsumer` 先按 `orderNo` 查一次，存在就跳过；DB 上还有 `order_no` 唯一索引双保险。

**面试答法**：
> "下单接口只做 Redis 预扣和发消息，三次 DB 写放给消费者，接口 RT 从几十毫秒降到个位数。
> 代价是最终一致，我实测过订单延迟 39 秒落库，所以前端不能假设下单后立刻能查到。"

## 8. 延时关单（TTL + 死信队列）

### ① 代码位置

`RabbitMqConfig` 里声明了三个队列：

```
movie.order.delay.queue    x-message-ttl=30分钟，无消费者
        │ 到期 → 死信
        ▼
movie.order.timeout.queue  → orderTimeoutConsumer
```

### ② 为什么不轮询数据库

轮询要扫 `status=0 AND pay_expire_time < now()`，订单量大时是全表扫描，而且有延迟。
TTL + 死信是"消息自己到期"，零轮询。

### ③ 必须知道的坑：队头阻塞

RabbitMQ **只检查队头消息是否过期**。如果队列里混着不同 TTL 的消息（比如 30 分钟和 2 小时），
后面的短 TTL 消息会被前面的长 TTL 消息**堵住**，实际延迟远大于预期。

本项目所有订单固定 30 分钟 TTL，所以不受影响；如果要不同时长，得用延迟插件或时间轮。

**面试答法**：
> "延时关单用 TTL 加死信队列，不轮询数据库。但它有个队头阻塞的坑：TTL 只对队头生效，混用不同 TTL 会互相堵，所以我这里统一 30 分钟。"

## 9. 库存释放幂等（本项目最"生产级"的一段）

### ① 代码位置

`OrderServiceImpl.releaseStock` + `stock_release_log` 表

### ② 问题：MQ 是至少一次投递，同一条消息会被处理两次

场景：用户取消 → 发"释放库存"消息 → 消费者加回 1 张 → **ack 丢了** → Broker 重投 → 又加 1 张 → **库存变 11**（实际只有 10）→ 超卖。

### ③ 解法：唯一键做闸门

```java
@Transactional(rollbackFor = Exception.class)
public void releaseStock(StockReleaseMessage message) {
    try {
        stockReleaseLogMapper.insert(log);        // order_no 上有唯一键
    } catch (DuplicateKeyException e) {
        return;                                    // 插不进去 = 处理过了
    }
    // 先改 DB（权威），再回补 Redis
}
```

**为什么用唯一键而不是"先查再插"**：查和插之间有并发窗口（TOCTOU），两个线程会都查到"没有"然后都插进去。唯一索引是数据库层面的原子约束。

**为什么加 `@Transactional`**：插日志和改库存要同生共死 —— 否则日志插了、库存没改，这张票就永远还不回去了。

**为什么 Redis 放最后**：Redis 不参与事务、回滚不了，所以不可回滚的操作必须放最后。

**注意**：唯一键用的是 `order_no` 单列，不是 `(order_no, reason)` —— 语义是"一张订单的库存只释放一次"，与原因无关。

## 10. 事务边界：`AfterCommit`（已建，未接入）

### ① 代码位置

`framework/tx/AfterCommit.java` —— **工具类已写好，但 4 个发送点还没用上**。

### ② 问题

`cancel` / `refund` / `closeTimeoutOrder` 都是：

```java
@Transactional
public void cancel(...) {
    trainOrderMapper.update(...);          // 改状态
    producer.sendStockRelease(msg);        // ← 消息立刻发出去，不受事务控制
}                                          // 事务才提交
```

如果 commit 失败（死锁/连接断），**订单回滚了、但库存已经还回去了** → 用户一支付就白拿一张票。

### ③ 正确做法

```java
AfterCommit.run(() -> producer.sendStockRelease(msg));
```

`TransactionSynchronization#afterCommit` 只在提交成功后执行。

### ④ 但 afterCommit 只解决一半

- **发早了**（事务回滚但消息已发）→ ✅ 解决
- **发丢了**（提交后发送失败）→ ❌ 没解决，库存永远还不回去

彻底解决要**本地消息表**：业务改动 + 待发消息写同一个事务，后台任务扫描重发。

**面试答法（这段非常加分，因为你连"没做完"都能讲清楚）**：
> "我知道事务里发 MQ 有问题，工具类 `AfterCommit` 已经写好了，但还没接到 4 个发送点上，这是我下一步要改的。
> 而且 afterCommit 只解决'发早了'，'发丢了'要靠本地消息表，方案我清楚，还没落地。"

## 11. 订单状态机

### ① 状态

```
0 待支付 ──支付──► 1 已支付 ──退票──► 4 已退票
   │                   │
   │取消/超时          │（出票，未实现）
   ▼                   ▼
 2 已取消            3 已出票 ──退票──► 4
```

### ② 实现方式：条件 UPDATE + 影响行数

```java
int rows = mapper.update(null, new LambdaUpdateWrapper<MovieOrder>()
        .eq(MovieOrder::getOrderNo, orderNo)
        .eq(MovieOrder::getStatus, 0)          // ← 源状态写进 WHERE
        .set(MovieOrder::getStatus, 1));
if (rows == 0) return;   // 状态已经变了，幂等返回
```

### ③ 为什么不"先查再改"

| 写法 | 问题 |
| --- | --- |
| 先 `SELECT status` 再 `UPDATE` | 查完到改之间状态可能被改（TOCTOU）；多一次 DB 往返；并发下两个请求都能通过检查 |
| 条件 UPDATE | 判断和修改在同一条 SQL，数据库保证原子；影响行数就是"是不是我改的" |

这就是 **CAS 思想落到 SQL**。

### ④ 一个易错细节

退票允许 `status in (1,3)`，要用 `.in(...)` 而不是 `.eq(1).or().eq(3)` ——
后者在和其他条件组合时，会因为 AND/OR 优先级把越权条件绕过去。

## 12. MySQL：索引与事务

### ① 关键索引

| 表 | 索引 | 作用 |
| --- | --- | --- |
| `screening_seat` | `uk_screening_date_type (screening_id, show_date, ticket_type)` | 唯一键，保证一行库存；也是查询的覆盖索引 |
| `movie_order` | `uk_order_no` | 订单号唯一，消费端幂等双保险 |
| `movie_order` | `idx_user_id` | "我的订单" |

### ② 可以主动说的改进点

`movie_order` 查"我的订单"是 `WHERE user_id=? ORDER BY create_time DESC`，
现在只有 `idx_user_id`，排序会 **filesort**。应该建 `(user_id, create_time)` 复合索引，让排序也走索引。

### ③ 为什么"扣库存"用 `remain = remain - n` 而不是先查再算

`UPDATE ... SET remain = remain - n WHERE remain >= n` 是原子的，且条件保证了不会减成负数。
先查再算需要额外一次往返，并发下还会互相覆盖。

### ④ 事务

所有写操作都标 `@Transactional(rollbackFor = Exception.class)` —— 默认只回滚 `RuntimeException`，受检异常不回滚。

## 13. 可观测性

| 手段 | 实现 |
| --- | --- |
| traceId | 拦截器 `MDC.put("traceId", ...)`，logback 格式 `[%X{traceId}]` |
| 全链路 | 一次请求的所有日志带同一个 traceId，可按它 grep 出完整调用 |
| 健康检查 | Actuator `/actuator/health`，一次性确认 MySQL / Redis / RabbitMQ |

### 必须知道的坑：MQ 消费线程里 traceId 是空的

`MDC` 底层是 `ThreadLocal`，**不跨线程**。生产者线程 put 的值，消费者线程看不到。

解决：消息体里带上 traceId，消费端 `MDC.put` 还原；或者用 `TransmittableThreadLocal`。

**这个坑说出来非常加分** —— 证明你真看过日志，不是只看过教程。
