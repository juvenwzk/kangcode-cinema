### 1.1 状态一览（`train_order.status`）

| 值 | 状态 | 说明 |
| --- | --- | --- |
| 0 | 待支付 | 下单成功，等着付款 |
| 1 | 已支付 | 付过钱了 |
| 2 | 已取消 | 用户主动取消，或者 30 分钟没付钱 |
| 3 | 已出票 | 出票成功（本项目暂不实现，留给你扩展） |
| 4 | 已退票 | 退款成功（选做） |

### 1.1.1 先补状态常量（不补会直接编译报错）

P3 在 `OrderServiceImpl` 里只定义了 `STATUS_WAIT_PAY`（还有 `PAY_TIMEOUT_MINUTES`）。
P4 会用到 **已支付** 和 **已取消** 两个状态，所以先把它们补上，跟已有的常量放一起：

```java
    /** 订单状态：0-待支付 */
    private static final int STATUS_WAIT_PAY = 0;      // ← P3 已经加过了，确认一下在不在
    /** 订单状态：1-已支付（P4 新增） */
    private static final int STATUS_PAID = 1;
    /** 订单状态：2-已取消 / 已关闭（P4 新增） */
    private static final int STATUS_CANCELED = 2;

    /** 支付超时时间（分钟） */
    private static final int PAY_TIMEOUT_MINUTES = 30;  // ← P3 已经加过了
```

> ⚠️ 不加 `STATUS_PAID` / `STATUS_CANCELED`，下面 4-1、4-2、4-3 的代码会全部标红（`cannot resolve symbol`）。
> 这也是 P3 踩过的同类坑——**看到文档用了某个常量，先确认它在不在类顶部**。
>

> 同样要 `import com.kangcode.pojo.dto.StockReleaseMessage;`。

### 1.2 状态怎么流转

```
               下单成功
                  │
                  ▼
             ┌─────────┐
             │ 0 待支付 │
             └────┬────┘
    支付回调 ─────┤───── 用户取消 / 30 分钟超时
                  │                    │
                  ▼                    ▼
             ┌─────────┐          ┌─────────┐
             │ 1 已支付 │          │ 2 已取消 │ ──► 释放库存（Redis + DB 都加回去）
             └────┬────┘          └─────────┘
                  │
                  ▼
             ┌─────────┐
             │ 3 已出票 │
             └─────────┘
```

两条铁律：

1. **只有"待支付"能被改动**（付款、取消、关单都只认 `status = 0`）；
2. **只有"取消"和"超时"才释放库存**（付了钱的订单，超时消息来了也要忽略）。

### 1.3 为什么要用"SQL 条件更新"而不是 `if`

新手容易这么写：

```java
// ❌ 两条线程可能同时读到 status=0，都往下走
TrainOrder order = getByOrderNo(orderNo);
if (order.getStatus() == 0) {
    order.setStatus(1);
    update(order);
}
```

正确做法是把判断写进 SQL，**看影响行数**：

```java
// ✅ 只有一个线程能更新成功，另一个影响行数 = 0
int rows = trainOrderMapper.update(null, new LambdaUpdateWrapper<TrainOrder>()
        .eq(TrainOrder::getOrderNo, orderNo)
        .eq(TrainOrder::getStatus, 0)     // ← 关键：状态条件写进 SQL
        .set(TrainOrder::getStatus, 1));
if (rows == 0) { /* 说明状态已经变了，幂等返回 */ }
```

这就是"**乐观锁**"的另一种用法（和 P2 放票接口里 `@Version` 是一个思路）：
让数据库来保证"只有一个人能改成功"。

## 2. 任务 4-1：用户取消订单

![图 8 · 取消订单与退票（库存回补的两条路径）](diagrams/08-cancel-refund.png)

本任务对应图上**「路径 A · 取消订单」**那一列。图里另外画了「路径 B · 退票」作对比（第 6 节的内容），
两者最后都汇聚到 `railway.stock.release.queue`，**库存回补逻辑只写一份**（任务 4-4）。

> ⚠️ 图最底部那条「事务陷阱」务必看：**不要在 `@Transactional` 方法内部发 MQ 消息** ——
> 事务还没提交，消息已经到了消费者，消费者读到的是旧状态。

**文件**：`server/src/main/java/com/kangcode/server/service/impl/OrderServiceImpl.java`

### 2.1 完整代码

```java
    @Override
    @Transactional(rollbackFor = Exception.class)
    public void cancel(Long userId, String orderNo) {
        // ① 校验归属：只能取消自己的订单
        TrainOrder order = trainOrderMapper.selectOne(new LambdaQueryWrapper<TrainOrder>()
                .eq(TrainOrder::getOrderNo, orderNo)
                .eq(TrainOrder::getUserId, userId));
        if (order == null) {
            throw new BusinessException(ResultCode.NOT_FOUND);
        }

        // ② 只有"待支付"能取消；SQL 带 status 条件，影响行数为 0 说明状态已经变了
        int rows = trainOrderMapper.update(null, new LambdaUpdateWrapper<TrainOrder>()
                .eq(TrainOrder::getOrderNo, orderNo)
                .eq(TrainOrder::getStatus, STATUS_WAIT_PAY)
                .set(TrainOrder::getStatus, STATUS_CANCELED)
                .set(TrainOrder::getUpdateTime, LocalDateTime.now()));
        if (rows == 0) {
            // 走到这里说明状态已经不是"待支付"了。用专用错误码给前端更准的提示：
            // 1003 = 订单已支付，1004 = 订单已取消
            // （这里的 order 是上面查出来的，并发下可能略滞后，但只用于错误提示，够用）
            if (order.getStatus() == STATUS_PAID) {
                throw new BusinessException(ResultCode.ORDER_PAID);
            }
            throw new BusinessException(ResultCode.ORDER_CANCELED);
        }

        // ③ 发消息释放库存（取消 = 把票还回去）
        ticketOrderProducer.sendStockRelease(StockReleaseMessage.builder()
                .orderNo(orderNo)
                .trainId(order.getTrainId())
                .travelDate(order.getTravelDate())
                .seatType(order.getSeatType())
                .ticketCount(order.getTicketCount())
                .reason("CANCEL")
                .build());
        log.info("订单已取消 orderNo={}", orderNo);
    }
```

### 2.2 三个细节

| 细节 | 原因 |
| --- | --- |
| 查询时带 `userId` | 防止 A 用户取消 B 用户的订单（越权） |
| `@Transactional` | 状态更新失败要回滚 |
| 用 `reason="CANCEL"` 区分 | 超时关单是 `TIMEOUT`，排查问题时能分清是谁触发的 |

> **取消成功后为什么不是直接改库存，而是发消息？**
> 因为"回补库存"还可能被其它流程触发（超时关单），统一走一条消息通道，
> 代码只有一处，出问题也只查一处。这也是 MQ 的常见用法：**一个动作，多处复用**。

## 3. 任务 4-2：支付回调（幂等）

### 3.1 真实项目里支付是怎么走通的

```
我们的系统                          第三方支付平台（微信/支付宝）
   │                                      │
   │ ① 用户点"支付"，带订单号请求下单 ──────►│
   │ ② 平台返回支付链接/二维码             │
   │ ③ 用户付款                           │
   │ ④ 平台回调我们的接口（POST 订单号+流水号）│
   │◄─────────────────────────────────────┤
   │ ⑤ 我们验签 → 改订单状态为"已支付"      │
   │ ⑥ 返回 success（否则平台会一直重试）    │
```

两个重点：

1. **回调接口必须对未登录开放**（支付平台不可能带我们的 JWT token）；
2. **平台会重复回调**（没收到 success 就重试），所以接口必须**幂等**。

### 3.3 支付成功的业务逻辑（幂等的关键）

`OrderService` 接口新增：

```java
    /**
     * 支付成功（回调）：只有"待支付"能变成"已支付"，重复回调幂等返回
     */
    void paySuccess(String orderNo);
```

`OrderServiceImpl` 实现：

```java
    @Override
    @Transactional(rollbackFor = Exception.class)
    public void paySuccess(String orderNo) {
        // SQL 里带上 status = 0 条件：影响行数 = 0 说明已经支付过或已取消，直接幂等返回
        int rows = trainOrderMapper.update(null, new LambdaUpdateWrapper<TrainOrder>()
                .eq(TrainOrder::getOrderNo, orderNo)
                .eq(TrainOrder::getStatus, STATUS_WAIT_PAY)
                .set(TrainOrder::getStatus, STATUS_PAID)
                .set(TrainOrder::getPayTime, LocalDateTime.now())
                .set(TrainOrder::getUpdateTime, LocalDateTime.now()));
        if (rows == 0) {
            log.info("支付回调：订单不是待支付状态，幂等忽略 orderNo={}", orderNo);
            return;
        }
        log.info("支付成功 orderNo={}", orderNo);
    }
```

**为什么这样就幂等了？**

| 第几次回调 | SQL 影响行数 | 结果 |
| --- | --- | --- |
| 第一次 | 1 | 状态 0 → 1，记录 `pay_time` |
| 第二次 | 0 | 直接返回，什么都不改（`pay_time` 也不会被覆盖） |

> 真实项目里，`paySuccess` 前面还要加**验签**和**金额核对**，这里为了能本地跑通先省略。

## 4. 任务 4-3：30 分钟不支付自动关单

![图 7 · MQ 异步链路（下半部分就是本任务）](diagrams/07-mq-async.png)

本任务对应图上**「【二】超时关单：TTL + 死信队列」**那半部分，链路是：

```
下单成功 → railway.order.delay.queue（无消费者，消息在这里躺 TTL 30 分钟）
        → 到期变死信 → 自动转发 → railway.order.timeout.queue → OrderTimeoutConsumer
        → 查订单状态：还是待支付才关单，已支付直接丢弃消息
```

> **两个队列别搞混**（这是最容易弄反的地方）：
>
> | 队列 | 常量 | 有没有消费者 | 作用 |
> | --- | --- | --- | --- |
> | `railway.order.delay.queue` | `MqConstant.ORDER_DELAY_QUEUE` | **没有** | 消息在这儿躺满 TTL |
> | `railway.order.timeout.queue` | `MqConstant.ORDER_TIMEOUT_QUEUE` | **有**（`OrderTimeoutConsumer`） | 真正触发关单 |
>
> 下单时消息发到 **delay** 队列；躺够 TTL 变成死信后，由 `x-dead-letter-routing-key` 转发到 **timeout** 队列。

注意图左下角解释了**为什么不用「消息级 TTL」**：队列先进先出，队头消息没过期会挡住后面所有消息。

### 4.1 思路：用 RabbitMQ 的"延时队列"

RabbitMQ 本身没有"30 分钟后投递"的功能，但可以用**TTL + 死信队列**自己拼一个：

```
下单成功
   │ 发消息（不带消费者）
   ▼
┌──────────────────────┐
│ delay 队列            │   消息在这里躺 30 分钟（x-message-ttl=1800000）
│ 没有消费者            │
└──────────┬───────────┘
           │ 时间到了 = 消息"死"了
           │ 自动转发到 x-dead-letter-routing-key 指定的队列
           ▼
┌──────────────────────┐
│ timeout 队列          │   消费者收到消息 → 关单 + 释放库存
└──────────────────────┘
```

关键就是队列上的三个参数：

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `x-message-ttl` | 1800000（30 分钟） | 消息在这里最多活多久 |
| `x-dead-letter-exchange` | `""`（默认交换机） | 到期后投到哪个交换机 |
| `x-dead-letter-routing-key` | `railway.order.timeout.queue` | 到期后进哪个队列 |

队列声明代码（**P3 第 5.3 节已经写好了，这里是抄过来给你对照确认的**）：

> ⚠️ **不要往 `RabbitMqConfig` 里再粘一遍**——那样会出现重复的 `orderDelayQueue()` 方法 /
> 重复 Bean，应用启动直接失败。 对照一下**确认内容一致**即可。

```java
    /** 支付超时时间（毫秒），默认 30 分钟；测试时可以配成 10000（10 秒） */
    @Value("${order.pay-timeout-millis:1800000}")
    private int payTimeoutMillis;

    @Bean
    public Queue orderDelayQueue() {
        Map<String, Object> args = new HashMap<>();
        args.put("x-message-ttl", payTimeoutMillis);
        args.put("x-dead-letter-exchange", "");
        args.put("x-dead-letter-routing-key", MqConstant.ORDER_TIMEOUT_QUEUE);
        return new Queue(MqConstant.ORDER_DELAY_QUEUE, true, false, false, args);
    }
```

> **坑（我实测踩到了）**：队列参数是"创建时写死"的。
> 如果队列已经存在，再改 `x-message-ttl` 重新声明会报 `PRECONDITION_FAILED`。
> 想改 TTL，**二选一**：
>
> 1. 去 RabbitMQ 管理台（`http://43.166.0.94:15672`，`admin / 123456`）把
>    `railway.order.delay.queue` **删掉**，再重启应用；
> 2. 或者换一个队列名——改 `common/src/main/java/com/kangcode/common/constant/MqConstant.java` 里
>    `ORDER_DELAY_QUEUE` 的值（例如 `railway.order.delay.queue.t2`）。
>    **改这一处就够了**：队列声明和发送消息引用的都是这个常量，别的地方不用动。
>
> 我在测试时就是**换了个队列名**来跑不同 TTL 的场景。

### 4.2 发送延时消息（P3 已经写好，下单时自动发）

```java
    /** 支付超时消息：先丢进延时队列，躺够 TTL 才会进关单队列 */
    public void sendOrderTimeout(OrderTimeoutMessage message) {
        rabbitTemplate.convertAndSend(MqConstant.ORDER_DELAY_QUEUE, message);
        log.info("已发送支付超时延时消息 orderNo={}", message.getOrderNo());
    }
```

### 4.3 消费者

新建：`server/src/main/java/com/kangcode/server/mq/OrderTimeoutConsumer.java`

```java
package com.kangcode.server.mq;

import com.kangcode.common.constant.MqConstant;
import com.kangcode.pojo.dto.OrderTimeoutMessage;
import com.kangcode.server.service.OrderService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.stereotype.Component;

/**
 * 支付超时消费者：延时队列到期后收到消息 -> 关单 + 释放库存
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class OrderTimeoutConsumer {

    private final OrderService orderService;

    @RabbitListener(queues = MqConstant.ORDER_TIMEOUT_QUEUE)
    public void onMessage(OrderTimeoutMessage message) {
        log.info("收到支付超时消息: {}", message);
        orderService.closeTimeoutOrder(message.getOrderNo());
    }
}
```

### 4.4 关单逻辑

`OrderService` 接口新增：

```java
    /**
     * 支付超时关单：仍然是"待支付"就改成"已取消"，并发消息释放库存
     */
    void closeTimeoutOrder(String orderNo);
```

`OrderServiceImpl` 实现：

```java
    @Override
    @Transactional(rollbackFor = Exception.class)
    public void closeTimeoutOrder(String orderNo) {
        int rows = trainOrderMapper.update(null, new LambdaUpdateWrapper<TrainOrder>()
                .eq(TrainOrder::getOrderNo, orderNo)
                .eq(TrainOrder::getStatus, STATUS_WAIT_PAY)   // ← 已支付的订单不会被关掉
                .set(TrainOrder::getStatus, STATUS_CANCELED)
                .set(TrainOrder::getUpdateTime, LocalDateTime.now()));
        if (rows == 0) {
            log.info("支付超时消息：订单已支付或已取消，忽略 orderNo={}", orderNo);
            return;
        }

        TrainOrder order = trainOrderMapper.selectOne(new LambdaQueryWrapper<TrainOrder>()
                .eq(TrainOrder::getOrderNo, orderNo));
        ticketOrderProducer.sendStockRelease(StockReleaseMessage.builder()
                .orderNo(orderNo)
                .trainId(order.getTrainId())
                .travelDate(order.getTravelDate())
                .seatType(order.getSeatType())
                .ticketCount(order.getTicketCount())
                .reason("TIMEOUT")
                .build());
        log.info("订单支付超时，已关单 orderNo={}", orderNo);
    }
```

> 注意那个 `.eq(TrainOrder::getStatus, STATUS_WAIT_PAY)`：
> 用户如果先付了钱，30 分钟后延时消息照样会到，但**影响行数 = 0，订单不会被误关**。
> 这一行就是"状态机"在代码里的体现。

## 5. 任务 4-4：把库存还回去（取消 / 超时共用）

### 5.1 消费者

新建：`server/src/main/java/com/kangcode/server/mq/StockReleaseConsumer.java`

```java
package com.kangcode.server.mq;

import com.kangcode.common.constant.MqConstant;
import com.kangcode.pojo.dto.StockReleaseMessage;
import com.kangcode.server.service.OrderService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.stereotype.Component;

/**
 * 释放库存消费者：把取消/超时订单占用的票还回 Redis 和 DB
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class StockReleaseConsumer {

    private final OrderService orderService;

    @RabbitListener(queues = MqConstant.STOCK_RELEASE_QUEUE)
    public void onMessage(StockReleaseMessage message) {
        log.info("收到释放库存消息: {}", message);
        orderService.releaseStock(message);
    }
}
```

### 5.2 回补逻辑（Redis 和 DB 都要加）

`OrderService` 接口新增：

```java
    /**
     * 消费释放库存消息：Redis 回补 + DB 回补
     */
    void releaseStock(StockReleaseMessage message);
```

`OrderServiceImpl` 实现：

```java
    @Override
    @Transactional(rollbackFor = Exception.class)
    public void releaseStock(StockReleaseMessage message) {
        // ① Redis 回补：库存本来就是从这里扣的
        String key = RedisKeyConstant.ticketStockKey(
                message.getTrainId(), message.getTravelDate().toString(), message.getSeatType());
        stringRedisTemplate.opsForValue().increment(key, message.getTicketCount());

        // ② DB 回补：直接让 MySQL 做 remain = remain + n，避免"先查后改"被并发覆盖
        int rows = trainSeatMapper.update(null, new LambdaUpdateWrapper<TrainSeat>()
                .eq(TrainSeat::getTrainId, message.getTrainId())
                .eq(TrainSeat::getTravelDate, message.getTravelDate())
                .eq(TrainSeat::getSeatType, message.getSeatType())
                .setSql("remain = remain + " + message.getTicketCount()));

        log.info("库存已回补 key={} count={} DB影响行数={} reason={}",
                key, message.getTicketCount(), rows, message.getReason());
    }
```

> 为什么用 `setSql("remain = remain + n")` 而不是"先查出来再 `updateById`"？
> 因为两个取消请求同时到达时，"先查后改"会互相覆盖（读到同一个旧值）。
> 让 SQL 自己在数据库里做加法，就不会丢更新。
> （`n` 是我们自己消息里的整数，拼进 SQL 没有注入风险；更严谨的写法是 `setSql("remain = remain + {0}", count)`。）

> ### ⚠️ 这段有个"不完美"的地方，要心里有数
>
> **Redis 先加、DB 后加**。 如果 DB 那一步抛异常（比如连接断了），
> `@Transactional` 只能回滚 DB，**Redis 的 `increment` 是回不来的** ——
> 结果就是"缓存多了一张票、DB 没多"，两边不一致。
>
> 单看这一处，更严谨的做法是**把顺序反过来**（先 DB 后 Redis），并让 DB 失败时抛出异常、让消息重试。
> 本项目为教学简化保留了这个顺序，**靠 P2 的定时对账任务兜底**——
> `StockReconcileTask` 会周期性比对 Redis 和 DB，把对不上的修回来。
>
> 想自己改好：把 `increment` 挪到 `update` 之后，并且 `rows == 0` 时抛异常触发重试。
> （前提是消费端幂等，否则重试会重复回补 —— 我们靠"状态只能从 0 变 2 那一次"来保证。）

## 6. 任务 4-5：退票（选做）

思路和取消几乎一样，多两步：

```
用户申请退票
  ├─ 校验：订单是自己的、状态是 1（已支付）或 3（已出票）
  ├─ 改状态：1/3 → 4（已退票），条件写进 SQL
  ├─ 发释放库存消息（reason = "REFUND"）
  └─ 真实项目还要调用支付平台的"退款接口"，并落一条退款流水
```

**接口**：`POST /api/order/{orderNo}/refund`（和 `/cancel` 对称，加到 `OrderController`）。

**关键代码**——状态条件那一步要这么写：

```java
// ✅ 正确：用 in(...) 一次表达"状态是 1 或 3"
int rows = trainOrderMapper.update(null, new LambdaUpdateWrapper<TrainOrder>()
        .eq(TrainOrder::getOrderNo, orderNo)
        .eq(TrainOrder::getUserId, userId)     // 只能退自己的单
        .in(TrainOrder::getStatus, 1, 3)       // 已支付 或 已出票
        .set(TrainOrder::getStatus, 4));       // → 已退票
if (rows == 0) {
    throw new BusinessException(ResultCode.BUSINESS_ERROR.getCode(), "该订单不能退票");
}
```

> ### ⚠️ 千万别写成 `.eq(status, 1).or().eq(status, 3)`
>
> 这里有两个坑，第二个尤其危险：
>
> 1. **裸 `status` 不是合法 Java** —— 要用方法引用 `TrainOrder::getStatus`，否则编译不过；
> 2. **就算补成方法引用，`.or()` 不加分组也会出事**。 它拼出来的 SQL 是：
>    ```sql
>    order_no = ? AND user_id = ? AND status = 1 OR status = 3
>    ```
>    `AND` 的优先级高于 `OR`，所以等价于：
>    ```sql
>    (order_no = ? AND user_id = ? AND status = 1) OR (status = 3)
>    ```
>    后半段 **把全表所有 `status = 3` 的订单都选中了** —— 越权改别人的单，外加数据错乱。
>
> 真要写 OR，必须显式分组：`.and(w -> w.eq(...).or().eq(...))`。
> 但"同一个字段取多个值"这种场景，**用 `.in(...)` 最省事、也最不容易错**。

可以先不做，等 P5 压测通过后再回来补。

### 8.3 超时关单：把 30 分钟改成 10 秒来观察

想快速验证超时关单，要动**三个地方**——只改一个，你会发现"没生效"。

**① 改 MQ 延时队列的 TTL**（`application-dev.yml`，**测试用**）：

```yaml
order:
  pay-timeout-millis: 10000   # 10 秒后就关单，方便测试；生产用 1800000（30 分钟）
```

> ⚠️ **改之前记得先删旧队列**！ 队列参数是**创建时写死**的，
> `railway.order.delay.queue` 早就被 P3 用默认值 `1800000` 建出来了，
> 直接重启应用会报 `PRECONDITION_FAILED`。
> 去管理台（`http://43.166.0.94:15672`）把它删掉，或者换个队列名（做法见 4.1）。

**② 同步改订单里的"支付到期时间"**（`OrderServiceImpl` 类顶部）：

```java
    /** 支付超时时间（分钟）：要和上面 MQ 的 TTL 对齐 */
    private static final int PAY_TIMEOUT_MINUTES = 30;   // 测试时可改成 1
```

> **这两个值的关系必须搞清楚**：
>
> | 值 | 位置 | 作用 |
> | --- | --- | --- |
> | `order.pay-timeout-millis` | MQ 延时队列 TTL | **真正决定什么时候触发关单** |
> | `PAY_TIMEOUT_MINUTES` | 写进 `order.payExpireTime` | 给前端看的"还剩多久"，以及业务判断 |
>
> 它们本来就应该对齐（30 分钟 ↔ 1800000 毫秒）。
> 测试时如果**只改 ①**，你会看到前端还写着"请在 30 分钟内完成支付"，但 10 秒后订单就被关了
> ——**这不是 bug，是这两个值没同步**。 知道这一点，能省你半小时排查。

**③ 重启应用**，让新 TTL 生效。

## 9. 常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 支付回调一直 401 | 回调接口被登录拦截器拦了 | 加到 `WebMvcConfig` 的放行名单（见 3.5） |
| 改 TTL 后启动报 `PRECONDITION_FAILED` | RabbitMQ 队列参数创建后不可改 | 先删旧队列，或换个队列名（具体做法见 4.1、8.3 ①） |
| 付了钱的订单被自动关掉 | 关单时没加 `status = 0` 条件 | `closeTimeoutOrder` 必须带状态条件（见 4.4） |
| 重复回调把 `pay_time` 覆盖了 | 没用"条件更新 + 影响行数"判断 | 见 3.3，影响行数为 0 就直接返回 |
| 库存回补多了 / 少了 | 同一张订单被释放了两次 | 在 `closeTimeoutOrder`/`cancel` 里保证**只有状态从 0 变成 2 的那一次**才发释放消息 |
| 事务回滚了但消息已经发出去 | "改库 + 发 MQ"不在一个事务里 | 生产做法是**本地消息表**（先写库、再定时投递）或 MQ 的事务消息。 **本项目为教学简化，是直接在事务方法里发的**——也就是说这个风险真实存在（见第 2 节开头的提示）。 知道有这回事、将来上生产要换掉就行，本阶段不展开 |
| 消费者一直重试同一条消息 | 消费逻辑抛异常 | 消费端要保证幂等（我们靠订单号唯一索引 + 先查后插），必要时配死信队列人工处理 |
