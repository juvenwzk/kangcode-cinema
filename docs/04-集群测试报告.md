# 集群测试报告

> 测试时间：2026-10-27
> 目标：验证「多实例 + nginx 负载均衡」下，高并发扣减、会话、缓存、幂等这些机制是否还是对的。

---

## 1. 测试环境

| 项 | 配置 |
| --- | --- |
| 机器 | Intel i5-14450HX（10 核 16 线程）/ 16 GB 内存 |
| JVM | JDK 21，两个实例各约 500 MB 常驻 |
| 中间件 | MySQL 8（本机 3306）、Redis（本机 6379）、RabbitMQ（远程 43.166.0.94） |
| 网关 | nginx 1.30（Windows 版），80 / 200 双端口 |
| 压测工具 | `scripts/loadtest.py`（纯标准库，线程 + `http.client` 连接复用） |

> 机器可用物理内存长期只有 0.5 GB 左右，两个 JVM 已经是这台机器的上限。
> 这也直接导致后面性能数据波动较大，看量级即可，不要当基准。

## 2. 拓扑

```
压测脚本 / 浏览器
      │  http://127.0.0.1:200
      ▼
   nginx（upstream 轮询 + 故障转移）
      ├── 127.0.0.1:8080  node-A ─┐
      └── 127.0.0.1:8081  node-B ─┤
                                 ├─→ MySQL  movie
                                 ├─→ Redis  （锁 / 余票 / 幂等 / token / 布隆）
                                 └─→ RabbitMQ（下单消息，两个实例竞争消费）
```

## 3. 检查项与结果

| # | 检查项 | 方法 | 结果 |
| --- | --- | --- | --- |
| 1 | 负载均衡 | 连打 40 次 `/api/cinema/list`，读响应头 `X-Upstream-Addr` | **PASS** 8080=20 / 8081=20，严格轮询 |
| 2 | JWT 跨实例 | demo 在 A 登录 → 拿 token 打 B 的 `/api/order/my`；demo02 反向再来一次 | **PASS** 双向 200 |
| 3 | 余票缓存共享 | 重置票池 100 → 删缓存 → A 查一次 → B 查一次 | **PASS** 两边都返回 100，全集群只回源 MySQL 1 次 |
| 4 | 幂等键跨实例 | A 首单成功，紧接着把同一请求打到 B | **PASS** A=200，B=1002「请勿重复下单」 |
| 5 | 跨实例并发不超卖 | 12 个用户同时抢 10 张，请求按序数交替发往 A/B | **PASS** 成功 10，DB 余票 0，Redis 余票 0，订单 +10 |
| 6 | 订单号全局唯一 | 比对 `COUNT(*)` 与 `COUNT(DISTINCT order_no)` | **PASS** 77 单 / 77 个不同订单号 |

第 5 项的实际分发是 8080:4 / 8081:6（另一轮 6:4），说明并发请求确实跨了两个 JVM，
而不是被某一台吃掉 —— 这是这项测试有意义的前提。

### 关键点：为什么跨实例还能守住 10 张

- **锁在 Redis 里**：`screening:lock:{screeningId}:{date}:{type}` 由 Redisson 维护，
  两个 JVM 抢的是同一把锁，天然互斥；
- **扣减是 Lua 原子脚本**：`GET → 比较 → DECRBY` 在 Redis 单线程里一次做完，
  不存在"两台机器同时读到 99 然后各扣一次"；
- **DB 还有一道 `WHERE remain >= n`**：即使 Redis 被绕开，落库时也减不成负数；
- **幂等键、token、缓存都在 Redis**：换实例照样认，不需要会话粘滞（sticky session）。

## 4. 故障转移

停掉 8080（`taskkill`），立刻连打请求：

| 阶段 | 响应头 `X-Upstream-Addr` | 耗时 | 结果 |
| --- | --- | --- | --- |
| 故障瞬间（前 2 次） | `127.0.0.1:8080, 127.0.0.1:8081` | 1.01 s | 200（重试成功） |
| 之后 | `127.0.0.1:8081` | 3.7 ms | 200 |
| 8080 重启后 | 8080 / 8081 各 5 次 | 正常 | 自动回到轮询 |

`X-Upstream-Addr` 里出现两个地址，说明 nginx 先打到 8080 失败，再自动重试到 8081，
**客户端拿到的仍然是 200**。

故障瞬间的 1 秒是 `proxy_connect_timeout`。原先配 5s，实测 Windows 上节点被 kill 后
不会立刻回 RST，请求要等约 2s；调到 1s 后毛刺降到 1s 左右。

重启 8080 后 nginx 在 `fail_timeout`（10s）到期后自动把它加回轮询，无需 reload。

## 5. 性能

同一台机器、同一条链路（都经过 nginx），单实例 vs 双实例：

| 并发 | 单实例 | 双实例 | 说明 |
| --- | --- | --- | --- |
| 20 | 3736 QPS / P99 10ms | 3284~3588 QPS / P99 9ms | 基本持平 |
| 100 | 4179 QPS / P99 61ms | 2678 QPS / P99 189ms | 双实例反而更差 |

原因很直接：**两个 JVM 跑在同一台机器上，抢的是同一份 CPU 和内存**。
可用内存只剩 0.5 GB，双实例时 GC 更频繁，P99 被拉高。

所以：

- 单机上再加实例，**不会提升吞吐**，只会分摊故障风险；
- 集群要真正扩容，得部署到不同机器；
- 20 并发远没打满单实例（单机能跑 4000+），这个量级下谈扩展性没有意义。

所有查询都命中 Redis 余票缓存，**3000 次查询 0 次打到 MySQL**，缓存这块在集群下没有退化。

## 6. 测试中发现并修掉的问题

### 6.1 影院列表 500：缓存里躺着上一版的对象

现象：集群测试第 1 项连打 40 次，HTTP 全是 200，但日志里刷满

```
java.lang.ClassCastException:
  class com.kangcode.common.core.Result cannot be cast to class java.util.List
```

根因：重构时把 `@Cacheable` 从 Controller 挪进了 `CinemaServiceImpl.listCinemas()`，
方法返回类型从 `Result<List<CinemaVO>>` 变成了 `List<CinemaVO>`，
但 Redis 里 `movie:cache:cinema::list` 存的还是老版本序列化的 `Result` 对象。
反序列化出来是 `Result`，往 `List` 上强转就炸。

修复：`DEL movie:cache:cinema::list`，让新代码重新写一份。

> 教训：**改了 `@Cacheable` 方法的返回类型，升级时必须清掉对应的 Redis key**，
> 否则老缓存会把新代码打挂。缓存里的对象结构也是需要版本管理的。

顺带一提，这个错误 HTTP 状态码是 200、`code` 却是 500，压测脚本只看状态码就会漏判 ——
后面所有检查都改成读响应体里的 `code` 了。

### 6.2 布隆预热日志打成 `{}`

```
INFO ... BloomFilterWarmUp - 布隆过滤器预热完成,登记{}个组合
```

`log.info("...{}...", ...)` 少传参数，占位符原样输出。已补上 `seats.size()`，
现在启动日志是「登记 3 个组合」。

### 6.3 下单成功 ≠ 订单已入库（测试误判为丢单）

现象：12 人抢 10 张，接口返回成功 10 单，但等 30 秒数据库只多了 6 单，看着像丢了 4 单。

排查：把两个实例日志里「已发送下单消息 / 收到下单消息 / 订单落库成功」三个计数拉出来比对 ——
22 条发送、22 条消费、22 条落库，**一条没丢**，只是消费得慢。

根因：下单走 RabbitMQ 异步落库，`/api/ticket/buy` 返回 200 时消息刚进队列。
本机内存紧张时消费者会被 GC 拖住，落库延迟从 0.6 秒到几十秒都出现过。

修复：脚本改成轮询等数据库追平（`--settle-timeout`，默认 60s），不再用固定 `sleep`。

> 这本身也是系统的一个真实特性：**下单接口返回成功只代表"预扣成功 + 消息已投递"**，
> 真正的订单要等消费者落库。用户立刻查「我的订单」有可能查不到，
> 靠 `StockReconcileTask` 对账任务兜底。要做到"下单即可查"，得改成同步落库 + 异步削峰，
> 或者引入本地消息表保证投递。

## 7. 复现步骤

```bash
# 1. 起两个实例（同一个 jar）
java -jar server/target/server-1.0.0-SNAPSHOT.jar --server.port=8080 --spring.profiles.active=dev
java -jar server/target/server-1.0.0-SNAPSHOT.jar --server.port=8081 --spring.profiles.active=dev

# 2. nginx upstream 指向两个节点后 reload
nginx -s reload

# 3. 跑集群检查（需要能调 mysql / redis-cli）
python scripts/loadtest.py cluster \
  --nodes http://127.0.0.1:8080,http://127.0.0.1:8081 \
  --mysql-exe "C:/Program Files/MySQL/MySQL Server 8.0/bin/mysql.exe" \
  --redis-cli "C:/Redis-8.8.0-Windows-x64-cygwin-with-Service/redis-cli.exe"
```

输出：

```
[PASS] 负载均衡      127.0.0.1:8080=20  127.0.0.1:8081=20
[PASS] JWT 跨实例    demo 在A登录→B校验 200，demo02 在B登录→A校验 200
[PASS] 缓存共享      A 查=100 B 查=100 回源=1 次 Redis=100
[PASS] 幂等跨实例    A 首次=200，B 重放=1002(请勿重复下单)
[PASS] 跨实例不超卖  12 人抢 10 张 → 成功 10，余 0，订单 +10（8080:4  8081:6）
[PASS] 订单号唯一    77 单 / 77 个不同订单号
```

## 8. 结论

- 分布式锁、Lua 预扣、幂等、缓存、布隆、JWT 全部对"实例数"无感，
  加机器不需要改代码，也不需要会话粘滞；
- 12 人抢 10 张、跨两个 JVM，成功数与余票严格对平，没有超卖也没有少卖；
- 单节点宕机时 nginx 自动切换，用户侧只有一次 1 秒的重试，之后无感；
- **单机多实例不会提升吞吐**，扩容要换机器；
- 遗留风险：下单消息没有 publisher confirm / 本地消息表，MQ 真丢消息时只能靠对账任务兜底。
