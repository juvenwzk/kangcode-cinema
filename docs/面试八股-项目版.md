## 第 1 章　项目怎么介绍

### 1.1 30 秒版（自我介绍时用）

> "我做过一个铁路购票系统，核心是**高并发下的余票扣减和订单一致性**。
> 技术栈是 Spring Boot + MyBatis-Plus + Redis + Redisson + RabbitMQ，前端原生 JS。
> 重点解决了三件事：不超卖、缓存三兄弟、订单最终一致。
> 压测过：12 个用户抢 10 张票，账目能对平；1000 次余票查询只有 4 次打到数据库。"

**为什么这么讲**：先给"解决了什么问题"，再给"两个可验证的数字"。有数字的自我介绍，面试官会顺着问下去。

### 1.2 2 分钟版（"详细说说你的项目"）

按 **背景 → 难点 → 做法 → 结果** 讲：

| 部分 | 说什么 |
| --- | --- |
| 背景 | 票务类系统，读多写少（查余票 >> 下单），且库存是**强一致**要求（不能超卖） |
| 难点 | ① 并发下不能超卖 ② 余票查询扛不住 DB ③ 下单链路太长（插订单+插明细+扣库存），接口慢 |
| 做法 | ① 三道防线：幂等键 + Redis Lua 原子预扣 + DB 条件更新 ② 余票缓存 + 缓存三招 ③ MQ 异步落库 + 延时关单 |
| 结果 | 并发抢票账平；1000 次查询 4 次打 DB；下单 RT 从几十 ms 降到几 ms |

### 1.3 必被问："你觉得这个项目最难的是什么？"

**别答"技术很多"**。给三个候选，挑一个讲：

| 候选 | 一句话概括 |
| --- | --- |
| A. 不超卖 | 三道防线分别防什么，为什么光有锁不够 |
| B. 缓存三招 | 三种"没命中"的成因不同，解法也不同（有实测数据） |
| C. 消息幂等 | MQ 是至少一次投递，重复是常态，必须自己处理 |

选 A 或 C 更好，因为能往深处走。

## 第 2 章　购票链路（最高频，必背）

### Q1 ★★★ 你怎么防超卖？

**分三层答**（对应 `TicketServiceImpl.buy`、`OrderServiceImpl.createOrder`）：

1. **防重复提交**：`order:dup:{userId}:{trainId}:{date}`，`setIfAbsent` 30 秒 —— 同一用户 30 秒内只能下一单。
2. **Redis Lua 原子预扣**：判断 `remain >= n` 和扣减在**一个脚本**里完成，不足返回 -1。
3. **DB 条件兜底**：`UPDATE ... WHERE remain >= n`，影响行数 0 说明扣不动 —— 即使 Redis 出了问题，DB 也不会扣成负数。

**追问：为什么不只用锁？**
锁只保证"同一时刻一个人进"，但"读余票 → 判断 → 扣减"如果是三条命令，中间仍可能被别的东西改。**锁保并发，原子保正确。**

### Q2 ★★★ 为什么用 Redisson 而不是 `SETNX`？

`SETNX` 自己实现锁有三个坑：

| 坑 | 具体问题 |
| --- | --- |
| 加锁和设过期不是原子的 | `SETNX` 成功后进程挂了 → 锁永不过期 → **死锁** |
| 释放时不校验持有者 | A 的锁超时释放了，B 拿到锁，A 执行完把 **B 的锁删了** |
| 不可重入、没有等待队列 | 同一线程重入就死锁；抢不到只能自己循环重试 |

Redisson 的解法（`getLock` 返回的 `RLock`）：

- 加锁/解锁都走 **Lua 脚本**，原子
- value 存 `{uuid:threadId → 重入次数}` 的 **Hash**，天然支持可重入和归属校验
- `tryLock(waitTime, ...)` 带等待队列（pub/sub 通知，不是无脑轮询）

### Q3 ★★★ 你传了 `leaseTime = 10s`，看门狗还生效吗？

**这是分水岭题，答错就露馅。**

> **不生效。** Redisson 只有在**不指定** `leaseTime`（传 -1）时才启用看门狗：默认 30 秒 TTL，每 10 秒续一次。
> 我在 `buy()` 里显式传了 `LOCK_LEASE_SECONDS = 10`，所以锁到期就释放，**不会续期**。

**为什么要这么设计（取舍）**：

| 选择 | 好处 | 风险 |
| --- | --- | --- |
| 不传 leaseTime（看门狗） | 业务跑多久锁就持多久，不会提前释放 | 进程被 kill 后靠看门狗线程续期，若整个 JVM 挂了，锁要等 30 秒才释放 |
| **传 leaseTime（我的选择）** | 最多 10 秒锁一定释放，**不会死锁** | 锁内业务超过 10 秒 → 锁提前释放 → 别的线程可能进来 |

我的临界区只有「Lua 预扣 + Redis INCR 生成订单号 + 发 MQ」，正常几毫秒，所以 10 秒足够。
**但如果 Redis 抖动或发生长 GC，理论上可能超时** —— 这是我知道的取舍。

> 面试时主动说出"这是取舍"，比假装没问题强得多。

### Q4 ★★ 抢锁等 3 秒等不到怎么办？会不会少卖？

会。抛 `1000 当前购票人数较多`，让用户重试。

> **这是"少卖不超卖"的主动选择**：宁可拒掉一些请求，也不让请求在锁上无限堆积把线程池打满。
> 压测数据：15 个用户抢 10 张，出现 5 个 `1000`，最终 10 成功 + 0 余票，**账是平的**。

### Q5 ★★ 锁的粒度为什么是 `trainId + date + seatType`？

按**库存行**加锁：一行库存 = 一把锁。

| 粒度 | 后果 |
| --- | --- |
| 全局一把锁 | 所有车次互相阻塞，吞吐极差 |
| 用户级锁 | 同车次不同用户仍会并发扣同一行 → **超卖** |
| **库存行级（我的做法）** | 互斥范围刚好等于"会被并发修改的那一行" |

### Q6 ★★ 预扣成功了，但订单没落库怎么办？

三道兜底：

1. 下单消息进 MQ，消费者落库（幂等：先按 `order_no` 查 + 唯一索引）
2. 下单时发 30 分钟**延时消息**，超时未支付 → 关单 + 发释放消息回补库存
3. **对账任务**每 5 分钟比对 Redis 与 DB，`Redis > DB` 时收紧 Redis（说明有预扣没落库的"幽灵单"）

## 第 3 章　缓存三招（你有实测数据，这章最能打）

### Q1 ★★★ 穿透、击穿、雪崩的区别？

**先说共性**：都是"缓存没命中，请求打到 DB"。**区别在"为什么没命中"**：

| 名字 | 为什么没命中 | 典型场景 |
| --- | --- | --- |
| **穿透** | 这个数据**根本不存在**，缓存永远不会命中 | 恶意查 `trainId=9999` |
| **击穿** | **一个热点 key 过期的瞬间**，大量请求同时未命中 | 热门车次余票 key 刚过期 |
| **雪崩** | **大批 key 同时过期** | 批量放票时统一预热，10 分钟后集体失效 |

> 一句话记忆：**穿透是"数据没有"，击穿是"一个 key 没了"，雪崩是"一片 key 没了"。**

### Q2 ★★★ 你分别怎么解决的？

对应 `TicketServiceImpl.queryRemain` / `loadFromDbAndCache`：

| 手段 | 代码 | 参数 |
| --- | --- | --- |
| 空值缓存防穿透 | 查不到时写 `EMPTY` | `EMPTY_TTL_SECONDS = 60` |
| 互斥重建防击穿 | `{key}#rebuild` 只有抢到锁的线程查库 | `10 秒` 过期 |
| TTL 抖动防雪崩 | `600 + random(0~60)` | `STOCK_TTL_SECONDS=600` |

**能拿出的数据**（用 MySQL `Com_select` 计数测的，50 个请求）：

| 配置 | 打到 DB 的次数 |
| --- | --- |
| 有空值缓存 | **5 次** |
| 关掉空值缓存 | **54 次** |
| 有互斥重建 | **5 次** |
| 关掉互斥重建 | **54 次** |

> **关掉任一招，DB 压力放大 10.8 倍。** 这句话比"我用了空值缓存"有说服力得多。

### Q3 ★★ 为什么空值 TTL 只有 60 秒，正常库存是 10 分钟？

- **空值是"临时不存在"**：可能是还没放票、或数据正在写入，很快会变。缓存太久会**误报"没有票"**。
- **正常库存要长**：减少回源次数，10 分钟 + 抖动足够。
- 另外空值 key 太多会占内存，短 TTL 能自动清理。

### Q4 ★★ 互斥重建锁为什么设 10 秒？

它只包住"查一次库 + 写一次缓存"，正常几毫秒。10 秒是**防御性上限**：万一持锁线程崩了，最多 10 秒后别人能重建，不会永久卡死。

配合后面的**自旋等待**：抢不到锁的线程不像无脑轮询，而是 `sleep(50ms)` 查 5 次缓存，拿到就返回；拿不到才退回直查 DB（兜底，不让请求失败）。

### Q5 ★★ TTL 抖动为什么能防雪崩？

如果一批 key 同时被预热（放票接口会批量写），固定 TTL 会让它们在**同一秒**集体过期。
加 `0~60 秒` 随机数后，过期时间被打散到一分钟内，DB 压力从"一个尖峰"摊平。

### Q6 ★★★ 缓存和 DB 的数据怎么保证一致？

**先摆明立场：不追求强一致，追求最终一致。**

| 环节 | 做法 |
| --- | --- |
| 读 | 缓存 miss → 查库 → 回填；查不到写 `EMPTY` |
| 写（扣库存） | Redis 先扣（主判断），MQ 消费者再扣 DB（权威数据） |
| 兜底 | 每 5 分钟对账：`Redis > DB` 就收紧 Redis；`Redis < DB` 视为"有预扣在途"，不动 |

**追问：为什么不用"先删缓存再更新 DB"那套（Cache Aside / 延迟双删）？**
因为本项目缓存的不是"对象"而是**计数器**，扣减必须走原子操作（Lua）；而且余票有"在途预扣"这种中间态，
用"删缓存"表达不了。所以用**双写 + 对账**更贴合。

### Q7 ★★★ 为什么用 Redis 存余票？不怕不一致吗？

**用数据回答**：压测时 1000 次余票查询，**只有 4 次打到 MySQL**。
缓存的价值是把 **99.6% 的读压力**从数据库上拿掉（这是 `Com_select` 前后差值实测的，不是估算）。

**不一致怎么办**：靠"扣减双写 + 定时对账"控制，接受秒级不一致。
票务场景下，"余票显示 5 实际 4"是可以接受的（用户点下单会被 Lua 拦住），"超卖"才是不可接受的。

## 第 4 章　消息队列

### Q1 ★★★ 为什么要用 MQ 异步落库？

**削峰 + 缩短接口 RT。**

下单接口原本要做：插订单、插明细、扣 DB 库存 —— 三次 DB 写 + 行锁竞争。
改成"只做 Redis 预扣 + 发消息"，把三次 DB 写挪到消费者，接口 RT 从几十 ms 降到几 ms，突发流量由队列缓冲。

**代价（要主动说）**：用户看到"下单成功"时订单还没落库 —— 最终一致。
我实测过一次：5 条订单延迟了约 39 秒才落库（当时机器负载高）。

### Q2 ★★★ 消息丢了怎么办？

**三处可能丢，分别对应三种机制**：

| 环节 | 可能丢 | 标准做法 | 我项目里 |
| --- | --- | --- | --- |
| 生产者 → Broker | 网络中断 | 生产者 confirm（`publisher-confirm`） | ❌ 没配 |
| Broker 内存 → 磁盘 | 断电 | 队列 durable + 消息 persistent | ✅ 默认已开 |
| 消费者处理 | 没处理完就 ack | 手动 ack + 失败 nack/重入队 | ⚠️ 用的是 auto ack + retry 3 次 |

> **诚实答法**："生产端 confirm 和死信队列我还没配，这是我这个项目的已知短板。"
> 面试官更在意你**知道自己缺什么**，而不是假装完备。

### Q3 ★★★ 重复消费怎么办？

**幂等。而且这是我项目里踩过的最典型的坑。**

`releaseStock` 原来长这样：

```java
stringRedisTemplate.increment(key, n);   // 每次都加
trainSeatMapper.update(... remain + n);  // 每次都加
```

同一条消息被投两次 → 库存多加一次 → **超卖**。

修法：落一张 `stock_release_log`，`order_no` 做唯一键；插得进去才继续，插不进去说明处理过，直接返回。

**为什么用唯一键而不是"先查再插"**：查和插之间有并发窗口（TOCTOU），两个线程会都查到"没有"然后都插进去。唯一索引在数据库层面是原子的，第二个必报错。

### Q4 ★★★ 延时关单怎么实现的？有什么坑？

**TTL + 死信队列（DLX）**：

```
下单 → delay 队列（x-message-ttl = 30分钟，无消费者）
         │  消息躺满 30 分钟
         ▼
      变成"死信" → 按 x-dead-letter-routing-key 转发
         ▼
      timeout 队列 → 消费者关单 + 发释放库存消息
```

**必说的坑（加分点）**：RabbitMQ **只检查队头消息是否过期**。
如果队列里混着不同 TTL 的消息，后面的短 TTL 消息会被前面的长 TTL 消息**阻塞**（队头阻塞）。
本项目所有订单都是固定 30 分钟 TTL，所以不受影响；如果要"30 分钟 + 2 小时"混合，就得上延迟插件或时间轮。

### Q5 ★ 为什么不用 Kafka？

本项目用 RabbitMQ 的两个理由：① 量级够用，运维简单；② RabbitMQ **原生支持延迟队列**（TTL + DLX），Kafka 要自己实现时间轮。

### Q6 ★ 消息积压怎么办？

先定位是"消费慢"还是"生产突增"：

| 原因 | 处理 |
| --- | --- |
| 消费逻辑慢（比如每条都查库） | 提高 `concurrency`、批量消费、加实例 |
| 消费一直失败重试 | **先修 bug**，别急着扩容（否则只是更快地重试） |
| 生产突增 | 临时扩容消费者，事后加限流 |

## 第 5 章　事务与状态机

### Q1 ★★★ `@Transactional` 什么情况下会失效？

| 场景 | 为什么 |
| --- | --- |
| **同类内部自调用** | 走的是 `this`，不经过代理，事务不生效（最常见） |
| 方法不是 `public` | CGLIB/JDK 代理拦不到 |
| 异常被 `catch` 掉没抛出 | 事务管理器感知不到异常 |
| 抛的是**受检异常** | 默认只回滚 `RuntimeException` 和 `Error`（要 `rollbackFor = Exception.class`） |
| 在**子线程**里操作 | 事务上下文在 `ThreadLocal` 里，不跨线程 |
| 表引擎是 MyISAM | 不支持事务 |

> 我项目里所有写操作都写了 `@Transactional(rollbackFor = Exception.class)`，就是为了避开第 4 条。

### Q2 ★★★ 在事务里发 MQ 会有什么问题？

**MQ 发送不受事务控制。**

```
begin ──► UPDATE 状态 ──► 发 MQ（消息真的出去了）
                              │  消费者已经在处理
         └─► commit 失败（死锁/连接断）
             ↑ 订单回滚了，但库存已经还回去了
```

解决：`afterCommit` —— 注册 `TransactionSynchronization`，只在提交成功后发。

**必须主动说局限**：`afterCommit` 只解决"**发早了**"，解决不了"**发丢了**"（提交后发送失败，没人重试）。
要彻底解决得上**本地消息表（outbox）**：业务改动 + 待发消息在同一个事务里写 DB，后台任务扫描重发。

### Q3 ★★★ 为什么用「带条件的 UPDATE」而不是「先查再改」？

```java
// ✅ 我项目里的写法
UPDATE train_order SET status=1 WHERE order_no=? AND status=0
// 影响行数 = 0 → 说明状态已经变了（别人改过），直接幂等返回
```

| 写法 | 问题 |
| --- | --- |
| 先 `SELECT status` 再 `UPDATE` | ① 查完到改之间状态可能被改（TOCTOU）② 多一次 DB 往返 ③ 并发下两个请求都可能通过检查 |
| **条件 UPDATE** | 判断和修改在一条 SQL 里，**数据库保证原子**；影响行数就是"是不是我改的"的答案 |

这就是 **CAS（Compare And Swap）思想落到 SQL 上**。

### Q4 ★★ 订单状态机是怎么实现的？

```
0 待支付 ──支付──► 1 已支付 ──退票──► 4 已退票
   │                   │
   │取消/超时          │（出票）
   ▼                   ▼
 2 已取消            3 已出票 ──退票──► 4
```

每个转换都是一条**带源状态条件的 UPDATE**，靠影响行数判断成败：

| 操作 | SQL 条件 | 失败响应 |
| --- | --- | --- |
| 支付 | `where status=0` | 已支付/已取消 → 幂等忽略 |
| 取消 | `where status=0` | `1004 订单已取消` / `1003 已支付不能取消` |
| 退票 | `where status in (1,3)` | `订单未支付，不能退票` / `该订单不能退票` |

> 用 `in(1,3)` 而不是 `.eq(1).or().eq(3)`，是为了避免 AND/OR 优先级把越权条件绕过去 —— 这个细节面试时提一句，显得你真踩过。

## 第 6 章　Redis 基础（配合项目答）

| 问题 | 答案要点 |
| --- | --- |
| 为什么快 | 纯内存 + 单线程无锁竞争 + IO 多路复用 + 高效数据结构（跳表/压缩列表） |
| 6.0 多线程 | **只有网络 IO 和协议解析多线程**，命令执行仍是单线程（所以 Lua 还是原子的） |
| 持久化 | RDB（快照，恢复快但可能丢最后一段）/ AOF（追加日志，安全但文件大）/ 混合持久化 |
| 过期策略 | 惰性删除（访问时检查）+ 定期删除（随机抽查） |
| 内存淘汰 | `allkeys-lru` / `volatile-lru` / `allkeys-lfu` / `noeviction`（默认，写满报错） |
| 大 key 危害 | 阻塞主线程、网络拥塞、删除耗时（用 `unlink` 异步删） |
| 热 key | 本地缓存（Caffeine）、key 拆分、读写分离 |
| Lua 为什么原子 | Redis 单线程执行脚本，脚本期间不会插入其他命令 |

> 你这项目里 **Lua 脚本**（`stockDeductScript`）是必被问的：为什么不直接 `DECR`？
> 答：`DECR` 不能判断"够不够"，会扣成负数；`判断 + 扣减` 必须在同一个脚本里。

## 第 7 章　MySQL

| 问题 | 答案要点 |
| --- | --- |
| 为什么用 B+ 树 | 矮胖（3 层能存千万级）、非叶子只存索引、叶子有链表适合范围查询 |
| 聚簇索引 vs 二级索引 | 聚簇索引叶子存整行；二级索引叶子存主键 → 查非索引列要**回表** |
| 覆盖索引 | 查询的列都在索引里，不用回表（`select remain` 走 `(train_id,date,seat_type)` 唯一索引就是覆盖） |
| 最左前缀 | `(a,b,c)` 能走 `a`、`a,b`、`a,b,c`，不能跳过 `a` |
| 隔离级别 | RC / RR / 串行化 / 读未提交；MySQL 默认 **RR** |
| MVCC | undo log 版本链 + ReadView，实现"读不加锁" |
| 间隙锁 | RR 下防幻读，锁住索引区间（所以 RR 下并发插入容易死锁） |
| 唯一索引 vs 普通索引 | 唯一索引插入时要检查唯一性（有额外开销），且**不能用 change buffer** 优化 |

**你项目里可以主动说的改进点**（显得你会看执行计划）：

> "`train_order` 只有 `idx_user_id` 和 `idx_train_date`。但'我的订单'是
> `WHERE user_id=? ORDER BY create_time DESC`，会走 `idx_user_id` 再 **filesort**。
> 应该建 `(user_id, create_time)` 复合索引，让排序也走索引。"

## 第 8 章　Java 基础

### Q ★★★ 线程池 7 个参数 + 为什么不用 `Executors`

| 参数 | 作用 |
| --- | --- |
| `corePoolSize` / `maximumPoolSize` | 核心/最大线程数 |
| `keepAliveTime` / `unit` | 非核心线程空闲存活时间 |
| `workQueue` | 任务队列（**决定什么时候扩容**） |
| `threadFactory` | 线程命名（排查问题必需） |
| `handler` | 拒绝策略：Abort / CallerRuns / Discard / DiscardOldest |

**为什么不用 `Executors`**（阿里规约）：
- `newFixedThreadPool` / `newSingleThreadExecutor` 用的是**无界队列** `LinkedBlockingQueue` → 任务堆积到 OOM
- `newCachedThreadPool` 的 `maximumPoolSize` 是 `Integer.MAX_VALUE` → 线程数爆炸到 OOM

### Q ★★★ `ThreadLocal` 为什么必须 `clear`

你项目里有两处：

| 用途 | 在哪 |
| --- | --- |
| `UserContext` 存当前登录用户 | `JwtInterceptor.preHandle` 写入，`afterCompletion` 清 |
| `MDC` 存 `traceId` | 同上 |

**不清的后果**：Tomcat 线程是**线程池复用**的。上一个请求的用户信息残留在 ThreadLocal 里，
下一个请求如果没有覆盖成功，就会**串号**（张三看到李四的订单）。

而且 `ThreadLocal` 的 value 挂在 `Thread` 上，线程不销毁 → **内存泄漏**。

### Q ★★ 为什么单机 `synchronized` 不够，要用分布式锁

`synchronized` 只锁"当前 JVM 内的对象"。多实例部署时，两个 JVM 各有一把锁，
**互相看不见** → 两个线程同时进入临界区 → 照样超卖。

而且 `synchronized` 锁的是**内存里的对象**，而库存是**Redis 里的值** —— 锁的对象和要保护的数据不在一个地方。

### Q ★★ `volatile` 和 `synchronized` 的区别

- `volatile`：保证**可见性**和**有序性**，不保证原子性（`i++` 仍然不安全）
- `synchronized`：三者都保证

## 第 9 章　Spring

### Q ★★★ 拦截器（Interceptor）和过滤器（Filter）的区别

| | Filter | Interceptor |
| --- | --- | --- |
| 所在层 | Servlet 容器（Tomcat） | Spring MVC（DispatcherServlet 之后） |
| 能否拿到 Bean | 不能直接注入（除非特殊处理） | **能**，本身就是 Spring Bean |
| 能否拿到 HandlerMethod | 不能 | **能**（知道要执行哪个 Controller 方法） |
| 执行顺序 | 先 | 后 |

> 你项目里用**拦截器**做 JWT 校验（`JwtInterceptor`），因为要注入 `JwtUtils` 和 `StringRedisTemplate` 去校验 token 是否在 Redis 里。

### Q ★★ Bean 生命周期

`实例化 → 属性注入 → BeanNameAware/BeanFactoryAware → BeanPostProcessor.before → @PostConstruct → InitializingBean.afterPropertiesSet → init-method → BeanPostProcessor.after（AOP 代理在这里生成）→ 使用 → @PreDestroy → DisposableBean.destroy`

### Q ★★ 循环依赖怎么解决的

**三级缓存**：

| 级别 | 存什么 |
| --- | --- |
| 一级 `singletonObjects` | 成品 Bean |
| 二级 `earlySingletonObjects` | 提前暴露的**半成品** |
| 三级 `singletonFactories` | 生成早期引用的工厂（为了 AOP 代理） |

> 局限：只能解决**单例 + setter/字段注入**的循环依赖，构造器注入和 prototype 都解决不了。

### Q ★ AOP 原理

动态代理：目标类有接口 → JDK 动态代理；没有接口 → CGLIB 生成子类。

## 第 10 章　三个能讲的故事（STAR，各 1 分钟）

### 故事 1：不超卖

- **S** 12 个用户并发抢 10 张票
- **T** 不能超卖，也不能扣成负数
- **A** 幂等键 → Redisson 锁 → Lua 原子预扣 → DB 条件更新兜底
- **R** 10 成功 + 2 个"抢锁超时" + 余票 0，**账平**

### 故事 2：缓存三招（有数据）

- **S** 余票查询扛不住 DB
- **T** 缓存要命中，且不能把 DB 打穿
- **A** 空值缓存 / 互斥重建 / TTL 抖动
- **R** 1000 次查询只打 4 次 DB；**关掉任一招，DB 查询放大 10.8 倍**

### 故事 3：消息重复导致超卖（最像"真实事故"）

- **S** 库存 10，取消后回补变 11
- **T** 找出为什么多了一张

- **R** 连续调 3 次释放，库存只 +2；集成测试覆盖

> **三个故事的区别**：1 讲"并发控制"，2 讲"缓存设计"，3 讲"分布式一致性"。
