### 核心数据（本机：应用+压测同机，MySQL 本地 / Redis 公网 remote）
- 读 有缓存：20 并发 QPS 168 / P99 131ms / **DB SELECT 4**；50 并发 QPS 411 / P99 183ms / **4**
  （1000 请求只打 4 次 DB → 缓存挡掉 99.6%）
- 读 无缓存：20 并发 QPS 268 / **404**；50 并发 QPS 493 / **1004**
- 穿透（车次 9999，50 请求）：有空值缓存 DB 5 次 / 421ms；关掉后 DB 54 次 / 876ms（**×10.8**）
- 击穿（冷 key，50 并发）：有互斥锁 DB 5 次 / 387ms；关掉后 DB 54 次 / 277ms（**×10.8**，且 QPS 反而更高 → 用延迟换 DB）
- 写场景：12 抢 10 → 10 成功 + 2×1001，账平；15 抢 10 → 10 成功 + 5×1000，账平
  落库核对：2026-12-28 / 12-29 各 10 订单 + 10 明细，余票 0

### 结论
- **不超卖**已被两档写场景证明（账平、余票不为负、订单=明细数）。
- **缓存的价值是保护 DB，不是降低延迟**：本机拓扑下 Redis 走公网 RTT，无缓存反而更快。
- 雪崩（TTL 抖动）未量化：属长周期现象（要等 10 分钟），报告中标注了复现方法与定性说明。

### 环境备忘

- 写场景每天只能用「没有 train_seat 记录」的日期（放票是增量）。
- 压测机与应用同机时，并发 100 会出现 83~99% `URLError`（本机端口/TIME_WAIT 耗尽），数据不可信。

- 用户把 `application-dev.yml` 的 Redis 从 `43.166.0.94`（公网、有密码）改为 **`localhost:6379`（无密码）**。

- 因此之前"缓存不降延迟/无缓存反而更快"的结论要修正为：**那是 Redis 走公网时代的结论，已过时**。

### 本地 Redis 下的 A/B（8081 端口自建实例，不碰用户 8080）
串行 30 次单请求（排除客户端争抢）：

| 配置 | avg | P50 | P95 |
| --- | ---: | ---: | ---: |
| 有缓存（本地 Redis） | 6.41ms | **4.39ms** | 20.62ms |
| 无缓存（直查 MySQL） | 11.92ms | **8.16ms** | 29.40ms |

→ **缓存快 1.86 倍**（P50 4.39 vs 8.16）。

并发对照：20 并发 974 QPS（有缓存）vs 865（无缓存）；50 并发 1035 QPS。
20→50 并发 QPS 几乎不涨 → **瓶颈已转移到 Python 压测客户端（GIL + urllib）**，此时并发数据没有参考价值，看串行延迟才准。
